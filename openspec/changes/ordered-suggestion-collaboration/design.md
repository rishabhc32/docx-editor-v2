## Context

Spike 5 (`spike/suggestion-log`, commit `bfd70f4a`, `spikes/suggestion-seq/`) is the evidence for this change. Its report records the item-list model, the Word item-kind matrix (65 kinds, 4,080 scenarios), the 12 engine placement rules, the collaboration sessions at six document sizes with an undo record, and the benchmark against the host's earlier stack (engine store, Yjs sync, the host's room guard). The spike code is not production code: it imports engine internals by relative path, drives the engine with `as never` casts, has no input validation, and mixes harness code with model code. This change ports the model into the engine and builds the client, the room core, and the host server integration around it.

Who an author is. The host's login gives the room a person: `OrderedPerson { id, name, org }`, a stable ID, a display name, and a company (empty for none). The room stamps that person on every change; a page never sets it. The ID decides whose an item is: one person in two tabs owns the same suggestions, and two people of one company with one name own only their own. The Word name, written as `w:author` for every room item, is `Name (Org)`, or `Name` with no company (`orderedAuthorName`, the one naming rule). A person is checked once where it enters (the login, the session options, a log, a frame, a checkpoint): an ID and a name of 1 to 256 characters after trim, a company of 0 to 256, and a Word name within the author cap. An item loaded from an uploaded Word file has no person: its `w:author` is the name Word saved, and it belongs to no person of the room. Person IDs stay inside the room's own files (the log and the checkpoints); every exported Word file carries names only.

Discussions are Word comments that travel through the room (D15): a comment, a reply and a resolve are changes the room checks, stamps with the person and orders, as it does a suggestion, and the Word file and the checkpoints hold them. Before, the host kept discussion text in its own backend and the document held only a marker, a Word comment whose whole text was `thread:<anchorId>`. Organisers decide in viewing mode through server messages.

## Goals / Non-Goals

**Goals:**

- One model for suggestions in a room: every character, object, mark and container token has an address that never changes during a room session; a suggestion is a label; a decision is a status change; decisions give one result in every order.
- One central order for changes; each client applies its unsent changes again on top of the server's changes with an undo record, never with copies of the document.
- The editor stays the only renderer and the only reader of Word form. The ordered model builds Word form for the changed paragraphs and publishes it through the existing port.
- Every change from a client is untrusted: validated, size-bounded, stamped with the login's person by the server, and checked by a per-change policy without reading the whole document.
- No silent drop: an edit the model cannot express is refused by name before it commits.
- Restart and deploy lose no confirmed change; a crash loses at most the unsaved tail whose author closed the page before the server came back.

**Non-Goals:**

- Peer-to-peer rooms. A server is always present.
- Replacing Yjs collaboration for other hosts. `full-document-yjs-collaboration` stays.
- Saving the item tree. A room is rebuilt from its Word file and its change log.

## Decisions

### D1. Representation

One ordered list of items per story part: the main document, each header part, each footer part, footnotes, endnotes. Item kinds: `text`, `atom` (picture, tab, break, note reference, whole field, equation), `zero` (bookmark, comment range, permission range, positional tab), `mark` (paragraph mark), `open` and `close` (link, control, table, row, cell, block control). Items are grouped in fragments of consecutive units of one insertion with the same labels. Fragments live in a summed B+ tree (`SumTree`) whose summaries count units, shown units and shown paragraph marks, so a position lookup and an edit are O(log n).

Labels: `by` (the suggestion that inserted the fragment, or none for file content), `dels` (the suggestions that struck it), `fmts` (format records), `props` (property records on marks and container tokens), `move` (move link), `retracted` (taken back by its own author), `taken` (the change whose deletion took it back, so the undo of that change shows it again). Nothing is removed or moved during a room session. A rejected insertion and an accepted deletion are hidden.

Alternatives rejected: keeping Word form (`w:ins`/`w:del` wrappers) in the list breaks addresses on every accept, split and join, so concurrent changes need per-kind rewrite rules (spikes 1 to 4 needed repair rules and still showed order dependence); a CRDT keeps a second full copy per browser and cannot express the server's policy.

### D2. Location and lane

`packages/core/src/collaboration/ordered/`, in the `collaboration` lane (environment `neutral`, may import `store`). Export subpath `@docx-editor.dev/core/collaboration/ordered`. The browser client and the room core both import it, so both run the same code. Files stay under the 1000-line lint cap; the target is under 500.

### D3. Word form at the boundary

Load turns a story part into items; compose turns items back into the part. Compose works per paragraph, so a change publishes only the paragraphs it touched. An untouched paragraph or block is the loaded node itself; one that holds an item the file labelled is always drawn from its items (`rebuilt`), so a take-back of a suggestion read from the file leaves no change record in it. Paragraph identity (`w14:paraId` and the editor node id) is kept on the paragraph mark item, so the editor's caret, layout caches and paragraph index keep working. New paragraphs take ids minted from the change id, the paragraphs of a block the engine builds (a new table, row or column) too: the engine mints their ids on a scratch part, against that part's paragraphs alone, so two new tables before one paragraph took the same ids and a reopen gave the second new ones. A container a change makes (a new control or link, or the second half of one that Enter split) has its open item's space as its node id, as a new paragraph has its mark's, so the editor's ops name it by that id and the client finds it (`openOfNode`). Save is compose of every story plus the untouched parts: `composeOrderedPackage(doc, base)` returns the whole package and `orderedPackageBytes` writes it with the engine's package writer. What a session adds outside the stories goes where Word reads it: hidden prompts as glossary blocks, each new link target as an external relationship of the story that holds it, and the comment parts as the model gives them (D15; the comments and commentsExtended parts, their content types and their relationships are made when the file has none). The styles part is the file's with the decided change records of its styles resolved (D15).

Word revision ids (`w:id`) are the same on every copy, whenever the copy composes. A file's revision keeps the id the file gave it. Every other id is a function of the suggestion's id and the mark's role, with no counter: a suggestion a change made has its id from the change id, so every copy writes the same `w:id`. A minted id is above 10^9, where a file's dense ids do not reach, and passes over every `w:id` the loaded parts hold. Two minted ids meet with a chance of about one in 1.1 billion for each pair; the engine then joins the two marks only when author and date also agree.

### D4. Placement

The engine decides where typed text lands near markers, deletions and containers (12 rules, `REPORT.md`, "Engine rules the matrix found"). `placement.ts` holds one copy of those rules. The item-kind matrix runs in CI against the engine; a difference fails the build, so drift is found when the engine changes. Where the engine and the list still differ for one edit, the client publishes the list's version of the paragraph, so the screen and the file always follow the list. Typing names the inline control the caret is in (`insert` with `inside`, the engine's `inside`): at that control's first or last character the text goes in it (`insideSite`), as the editor alone's keyboard types on in a control; a paste, a tab or a break there goes beside it (rule 5). The room once put typed text there beside the control too, so after a prompt was typed over, every key from the second one left the control (`client/editor-controls-edge-typing.test.ts`).

### D5. Policies (decided)

1. A second deletion of struck text does nothing on the struck part (Word and the host's earlier check).
2. A second format on formatted text replaces the first; the first suggestion is reported to a host callback (`onReplaced`). The second suggestion holds the first one's records with `replaced`, so its take-back gives them back; a checkpoint keeps each such record (D14, takeovers), and `orderedReplacedSuggestions(doc, suggestion)` names the suggestions it took records from, with their author, person, date, the change record's local name (`formattingKind`) and what they had set in the review queue's terms (`formattingChanges`, the engine's `changedFormatting`), so a page names them on the card (the host keeps no discussion for them). The same holds for a second change of a paragraph's, a table's, a row's or a cell's properties (Word keeps one change record for each). A direct edit by the organiser takes over no record. It shows at once on top of the pending record, and under a pending change made after it: compose draws a property's records from the first pending one in the order changes made them, pending and decided together, so the latest write shows on top, as Word shows it (`fromFirstPending`). It goes with a reject of that record, as in Word and the editor alone: Word keeps one record, the properties or the face before the first pending change, so a reject gives those back. The direct record names the pending suggestions whose change record shows when it is made (`over`), for a run's format, a paragraph's properties, a table's, a row's or a cell's, and a section's alike (`withFormat`, `withPropertyRecord`); a pending press that changes nothing writes no record, so a direct change over it stays. Compose leaves the direct record out once the suggestion that holds that record now is rejected: the one it was made over, or the one that took the record over later (policy 2). Before, the room kept a direct run or paragraph change live after the reject while the saved file dropped it (audit R1 row 27). A format press that changes no value makes no change and no record, and so does a paragraph press (`paragraphOpKeeps`: the engine's op, tracked, leaves the paragraph as it shows), as the engine's press makes none (a press made before another person's same format reached the presser): a run or a mark that already shows every value keeps its records, unless a pending format record is there, which a tracked press writes again under its own author as the engine does (Word's one record, the original under the latest author). The takeover is the organiser's alone: a party's change that would take over another person's pending record is refused (`policy-not-own`, `others_suggestions`), as the host's earlier check finds that person's suggestion gone or changed. The room judges it by what the change did (`checkApplied`, the apply's `replaced`), so every kind that takes a record over is covered. A press that restates every value a unit shows makes no change and no record when no change record is there to take over (`formatKeeps`, `edits/text.ts`), as the engine's press does: a format on its author's own new words writes none, so another person's bold over such words, made before that format reached them, leaves no suggestion (`client/editor-format-no-change.test.ts`, `__tests__/checkpoint-fold-decide.test.ts`); before, the room kept a record and a card that the file and a fold did not have.
3. Cards: a deletion next to an insertion by the same author (one person ID) is one card; words that deletion strikes too are part of it, not an insertion beside it (`insertionBeside`), so a card does not change with how struck words split into units (a direct deletion of some of them splits them, a fold joins them again), as the editor alone pairs a deletion only with an insertion that starts where it ends (before, a person's deletion of her own pending new words split in two joined their card live and not after a fold); changes inside another person's suggestion join that card (the host's card rule); a section's record on a paragraph mark joins another person's insertion only when every section the change sets is inside that insertion, as a table property record does (`joinsInsertion`): a page setup of several sections that another person's suggested break copied onto their new section keeps its own card, and its reject leaves the break, as the editor alone and Word do (a `w:sectPrChange` is a revision of its own, ECMA-376 Part 1, §17.13.5.32; before, the room rejected the break with it, `client/editor-section-break-card.test.ts`); what a person inserts in their own pending new row or cell in a later change joins that row's or cell's card (`ownContainer`), as the editor alone shows a new row and its words as one card and 2.x decided a row with what it holds (found by the live run of the 2.x flows, T step t15: the host's accept of the row left its words a suggestion; `client/editor-row-words.test.ts`). One card is one decision. Words a party types between two suggestions of one card of another person (their deletion and their insertion) are the party's own suggestion beside both, as the host's earlier check reads the Word file (it reads no cards): the card becomes two cards, as the Word file shows them (before, the room refused them as inside the card).
4. Enter in a control's prompt removes the prompt first, then breaks; a control that allows one line refuses Enter by name. Word 16.114 (2026-10-30, `~$p4-enter.docx` -> `~$p4-enter-tracked.docx`, Track Changes on) cannot hold a collapsed caret in a prompt: it selects the whole prompt, and Return replaces it. `w:showingPlcHdr` goes, the prompt's text goes with no `w:del`, and the control holds two empty paragraphs, the first mark a tracked `w:ins`. So in a block control Enter anywhere in the prompt's paragraph, its start and end too, removes the whole prompt for good: its units, and the marks of its other paragraphs; the caret's paragraph keeps its mark (`promptBreakSite`, `promptAround`). No glossary block keeps it (`ComposeContext.promptRemoved`), and the control shows a prompt again only when a decision empties it: Reject All gives Word's blank prompt (`~$p4-enter-rejected.docx`), and an accept keeps the two empty paragraphs. Taking the Enter back (its author's undo, or the organiser's undo of a direct Enter) brings the prompt back whole, as the editor's undo does (`change/settle-prompts.ts`, also for a one-paragraph prompt). The editor alone does the same (`content-control-prompt-enter.ts`). An inline control's prompt is no content to split, so Enter in it is refused by name (`break-in-container`). Backspace, Delete or a deletion across the paragraph mark between two paragraphs of a block control's shown prompt changes nothing, as a deletion of the prompt's text does: the prompt is no content, and Word changes a prompt only in Design Mode. The editor's tracked join does the same (`promptHoldsParagraph`). Inline prompts at two paragraphs' edges are outside the mark, so those paragraphs join as other text does. No join is refused for a prompt (the earlier `join-in-prompt` refusal is gone). A control inside a control keeps its own prompt: each control's prompt rule (hide, Enter, removal) takes only its own items (`ownItems`). A link in a prompt is part of the prompt, not a control in it: a load marks its words as the prompt's and not its edges, as the room makes a new link round prompt words (`markPrompt`), so content over the prompt takes the link and its words, whatever suggestion is on them, live and after a fold (before, a load marked the edges, the link read as a control in the prompt, and its words with a pending format stayed beside the value: the fold shapes session, seed 75; `__tests__/checkpoint-fold-prompts.test.ts`). Typing, a paste or Enter in a prompt that holds a control showing its own prompt replaces the outer prompt, wherever the caret is in the two, as the engine replaces the outermost (`placeholderControlForInsertion`; `promptSite`), and the inner control goes with it, as the engine's `clearPlaceholder` drops it (`promptParts`), when no edit reached it. One with a suggestion in it, one someone put there, or one with words of its own stays, so no suggestion goes with the prompt and no later decision takes the control away. The room once replaced the inner prompt and kept the inner control, so the page and the editor alone differed (`client/editor-controls-prompt-nested-typing.test.ts`). A control removed while it shows its prompt leaves the prompt as words, as the engine's unwrap does: the removal strikes the prompt units and puts plain copies in their place, so later edits treat them as text, and taking the removal back shows the prompt again. A block control's prompt of two or more paragraphs is replaced whole, as the engine's `clearPlaceholder` and Word replace it: while content fills the control, each prompt paragraph that holds nothing else goes and the paragraph typed in stays, and the whole prompt comes back once the control is empty. The prompt's marks carry the prompt flag, and a settle after every change shows or hides them (`change/settle-prompts.ts`), because a view counts the marks the model shows. Compose drops a gone prompt paragraph with no join, and a place in it (another person's caret in the prompt's other line) goes to the control's paragraph that stays, never past the control's end. Content that takes the place of a shown prompt drops the prompt's runs with any revision on them, as Word and the engine's `clearPlaceholder` do, and the save keeps the prompt as words only. So a party's content there is refused as nested while another person's pending suggestion is on the prompt, as today's check refuses it (`others_suggestions`; `room/over-prompt.ts`, acceptance quick pass 101). Where content goes in follows the edits' placement: a value or a building block always; at a caret inside an inline prompt or in a block prompt's paragraph, every edit but a table and Enter (Enter anywhere in a block prompt's paragraph, its edges too); at an inline prompt's edge, typed text only (words, a move, a note reference, a paste of one paragraph). `__tests__/room-policy-prompts.test.ts` checks each kind at each place against the save. The organiser's typing there is the editor alone's: the words take the face of the prompt's first words without the placeholder style, and no pending format of another person. The room shows no card for a suggestion on a prompt that content replaced, as the editor alone and the saved file have none, and an undo or a take-back brings the prompt and its card back. A decision that empties a control that names no prompt (`w:placeholder`) leaves Word's blank prompt: `w:showingPlcHdr`, an empty `w:sdtEndPr`, no `w:richText`, and one run of five spaces in no style, inline and block, with no glossary block (Word 16.114, 2026-10-30, samples `~$i6w-*` and `~$i6n-*`, Accept of a deletion and Reject of an insertion; the engine's `withDecisionPrompt`). The earlier oracle normalized Word's five spaces to an empty paragraph, so the engine left a block control empty; the oracle now compares them as recorded. Compose gives the blank prompt to a control that a decision on a suggestion emptied (`ComposeContext.decidedAway`: a rejected insertion or an accepted deletion, not a direct edit); a control that a direct edit emptied shows its type's prompt, as the engine's emptying edit does, and a control that names a prompt shows the glossary's. A paragraph that shows nothing inside a block control is published with its whole story, because only the story's drawing shows the prompt again. Typing into a control that an edit or a decision emptied replaces its prompt, as in the editor alone. Compose alone drew that prompt once, with no units in the list, so the editor's text differed from the list's and typing was refused (`text-differs`). Now a settle after every change gives such a control the prompt the engine writes (`change/settle-emptied.ts`): a decision's (`withDecisionPrompt`) or a direct edit's (`withRestoredPrompt`, the type's prompt). Its open item shows a prompt and holds the prompted properties, its original is the prompted control, and the prompt's units go in it, after the words that went, as a new control's do. From there the prompt rules hold as for a loaded prompt: typing replaces the prompt, a suggestion over it keeps it in the glossary, and it shows again when the words go. A decision is final, so the words it took away are marked gone, because they filled no prompt. A direct edit can be taken back (`revert`): once the words before the prompt show again, the prompt's units go for good and the control's open item and original are what they were before, as the engine's undo leaves the control. Every copy settles the same way, with the change's ids, in its undo record. The same settle covers the cases it first left out (`client/editor-controls-emptied-more.test.ts` compares each step with the editor alone and the save). Each part of a control that Enter split is a control of its own: its prompt's units go before the edge that ends it, and the Enter's suggestion on that edge is no pending insertion of the control; when the Enter is taken back, the parts are one control again and the units go (`unsplit`). A block control of several paragraphs keeps its first one, as the engine's emptied control does (`valueContent`): the later paragraphs' marks go, compose draws nothing of them and joins nothing (`isDroppedMark`), and taking the edit back gives them back; the direct edit counts as taken back once any word it took away shows again. Enter in a prompt that a decision showed, then its undo, shows that prompt again: a word that went for good is no content that blocks it (`settle-prompts.ts`). In a loaded prompt that showed again after a decision on the words that filled it, those words go for good at that decision (`settle-named-prompts.ts`), so a later Enter leaves two empty paragraphs and no prompt, as in the editor alone, and the control keeps naming the glossary block the engine kept its prompt in (`isFilledPrompt`). A copy of a control that Enter made is named by the engine's rule for an inline control (`partHolding`). A block control that holds a table is not emptied by taking its words: the table is content. A control that is another person's pending insertion, and whose words a direct edit takes away, is no longer a suggestion, as the editor alone drops that person's `w:ins` around it: the settle takes the insertion off the control's edges and off the words that went, so they filled no prompt, and gives the control its prompt; taking the edit back gives the insertion back (`untrack` in `settle-emptied.ts`). An author's own deletion of their pending words that empties a control shows its prompt too, with no revision, as Word does (Word for Mac, 2026-11-25, `w58-after-own-delete.docx`) and the editor alone now does (`withOwnEmptiedPrompts`): the prompt the control kept, else Word's blank prompt for a text control that names none, with no `w:sdtEndPr`. The settle gives it inside another person's pending deletion or insertion too (a struck row), as compose writes it. The prompt's units take the control's own insertion, as a fold reads them, and `untrack` takes an insertion off only when a direct edit took that person's words, never for the control's own author. Typing over that prompt extends the control's own insertion and keeps no glossary block, as the engine writes it plain inside (`insideOwnInsertion`; `ofOwnInsertion` in `compose/paragraph.ts`). Left as before: another person's pending control a decision emptied. A control that names a prompt in the glossary (`w:placeholder`) shows that prompt once the content that replaced its shown prompt went by a decision or a deletion (a reject of the typing, an accepted deletion of it, a direct deletion of it), as Word (ECMA-376 §17.5.2.25; typing drops the prompt's runs with no `w:del`, `~$p4-enter-tracked.docx`) and the editor alone show it; only taking the change back gives the replaced runs back. The room kept the loaded prompt's units and showed them again, so a reject of the organiser's suggested typing over a prompt that held another person's suggestion showed that suggestion and its card again, where the editor alone and a file saved before the reject had the glossary's prompt. Now a settle after every change (`change/settle-named-prompts.ts`) puts units of the glossary's prompt in place of the prompt's units at that moment only, so a later edit of the prompt stays: the other person's suggestion goes with the replaced units, and a party may then type over the prompt. A decision is final; a deletion that is not one, once taken back, gives the replaced units back. A unit the glossary's prompt replaced never shows again by the Enter rule (`restorePrompt`), and a gone prompt unit holds no suggestion for `others_suggestions` (`room/over-prompt.ts`). Left as before: a prompt or a glossary block of more than one paragraph in a block control. `client/editor-controls-prompt-named.test.ts` compares each step with the editor alone, with and without the other person's format. A control that names no glossary prompt keeps its own runs: the engine keeps them in the glossary when content replaces them, with any revision on them, so a reject shows them again with the other person's suggestion in the editor alone, the room and the save alike. Word shows its blank prompt there, as it keeps no glossary block: a difference of the engine's own (`editor/__tests__/suggesting-control-prompt-reject.test.ts`).
5. Enter inside a link or an inline control that holds several lines (plain text with `w:multiLine`, a group, a gallery; also a smart tag, custom XML, a direction run) splits it, as the engine's split does (task 3.5): a close item for each container (innermost first) goes before the new mark, and an open item for each (outermost first, a copy of the container's element under ids from the change) after it, which the container's own close item still ends. Markers at the caret go to the second part, as the engine sends them. A control that holds one line refuses it (`single-line-control`, by the engine's own line-break rule `propertiesHoldLineBreaks`); since task 9.13 the editor alone refuses it too, as Word does (the store's split op, `tree-op-split-controls.ts`, with the diagnostic `edit.single-line-control`). Word ignores Enter inside an inline rich text control, typed or untyped: no new paragraph, no revision, and typing at the same caret works (Word 16.114, 2026-10-30, samples `~$i2-split.docx` and `~$i2n-split.docx`). So the engine and the room refuse it there with the same name (`enterDividesControl`, task 9.14); a paste of several paragraphs there keeps the line rule only, because Word's paste there is not checked. Not checked in Word: Enter in a multi-line plain text control and in a group, which still split; links split in Word, as here. The split items carry the Enter's suggestion, but a decision on the Enter keeps the two containers, as the engine does and as a reopened Word file must (a rejected Enter leaves two links side by side, the same target and text); only taking the Enter back (its author's Backspace or undo, or the organiser's undo of a direct Enter) leaves one container again (`isSplitEdge`). When the container itself goes whole (its insertion rejected or taken back, both its own ends deleted), both halves go with it, whoever pressed Enter; a removal of one half strikes that half's own edges, so the other half stays (`client/editor-controls-made.test.ts`): found by the random four-person session, seed 23, where the organiser split a party's proposed link and a reject left one half (`__tests__/fields-apply.test.ts`). 6. A content control's lock binds every change, the organiser's and a party's, whatever a client sends (ECMA-376 Part 1 §17.5.2.23; a security rule). The editor alone is the reference (`contentControlLockRefusal`, the store's `locked`), and every copy refuses by the same name (`apply-refused`, reason `locked`). `contentLocked` and `sdtContentLocked` keep the content: typing, a tab or a break, a deletion that touches it (refused whole, never clipped), a format, Enter, a move out of it or into it, a note, a field, a picture or a paste there, a new link or a new control over its words or in them, its value, a change of a link, an object, an equation, a field or a form field in it, and the conversion of a note whose reference is in it. In a block control the lock also keeps its paragraphs: a join, a paragraph's or a mark's properties, a section break, a new list, a new table before a paragraph in it, and each row, column or cell change of a table in it. A row's deletion meets every control in its table, and a column's deletion every control of the table, as the engine's ops reach them; the engine's own op on the table refuses a new row or column there. The organiser's direct join also meets a locked inline control in either paragraph, because the engine's `joinParagraphs` rearranges both; a suggested join marks only the mark between them (`setParagraphMarkRevision`). `sdtLocked` and `sdtContentLocked` keep the control: its removal with or without its content, and the deletion of a paragraph, a row or a story that holds it. A content lock alone lets the control go whole, as Word and the engine let it go. A tag or title change is refused on any lock; a change of the lock alone asks only the controls around the control (Word's Properties dialog changes it). A lock holds for the controls inside the control (`resolveContentControlLock`). The lock is the one that shows now: the file's, or the organiser's later `control-property` change, so a lock set in the room binds the next change, and its undo frees the content. At a locked control's edges typed words go beside it, at its prompt too (the engine's `refusesTypedContent`; `promptSite`). Left allowed, as differences from the editor alone: a decision, a take-back and a revert of a suggestion inside a locked control (the editor alone refuses a decision there; in a room only the organiser decides, and a take-back gives words back), and a comment there (the editor alone refuses a comment strictly inside a locked control; a comment adds no words, and the host makes discussions on any text). A story replacement is refused for every lock value (the engine asks only the content lock there). The editor alone's opt-in `allowFormattingInLockedContent` has a room twin, `OrderedRoomOptions.contentLockPolicy`: the host sets it, `welcome` sends it, and the room and every copy apply each change with it. With it, a direct format (the organiser's, tracking off) passes the content lock, as the editor alone lets an untracked restyle pass; a property that hides text never passes, and a suggested format (a party's) stays refused, as the editor alone refuses a tracked restyle there (`formatPassesContentLock`). Without it the room keeps Word's reading: a format is an edit of the content. `placement.ts` (`refuseLocked`, `formatPassesContentLock`, `refuseContentLock`, `refuseLockedBlocks`, `refuseLockedWithin`, `refuseLockedAt`, `refuseLockedTable`), and `engineRefusal` gives the engine's own `locked` on the view the same name. Tests: `__tests__/room-locked-controls.test.ts` (every change kind, each lock value, organiser and party, inline, block and table, and every kind placed), `room-locked-places.test.ts` (a forged change from the acceptance run s100-short seed 1007, edges and prompts, a lock set in the room, nesting, objects, notes, links and fields inside, and the engine's own refusals), and `client/editor-locked-formatting.test.ts` (the room's policy: the organiser's format with undo, redo and a reopen; a party's format, and a format without the policy, refused).
7. A format reaches only a unit that can hold a run format (`holdsRunFormat`, `model/types.ts`): a unit in a run, or a simple field, whose runs take it. An equation has no run for the change record, so a format leaves it as it is, as Word does (Word for Mac, 2026-11-20: italic with Track Changes on over a paragraph that holds only a formula, and over words, a formula and words, formats the runs and the covered paragraph marks and leaves the formula untouched) and as the editor alone does (its format op changes runs only). Every path that writes a format asks the rule: a party's format and the organiser's direct one, a format on one's own new equation, a direct insertion under a pending format, and a link's character style. Load never gives an equation a format record. Tests: `__tests__/format-records-reopen.test.ts` (for every item kind of the matrix, a party's format and the organiser's direct one over the kind's paragraph and its mark, a new link over an equation, and a format over a pasted equation: the format records and the run properties after a save and reopen equal the live ones) and `client/editor-equation-format.test.ts` (a host's format change with real editors and one room).

### D6. Change format

JSON, version field `v: 1`. Client fields: `id` (sender namespace and counter), `part`, `kind`, places (`place`, or `from` and `to`, each `{ space, offset }`, or a paragraph-mark place `{ mark: { space, offset } }`), and the kind's payload. The caret field is `place`, not `at`, because `at` is the server's clock field. Server fields, never accepted from a client: `n` (order number), `by` (from the login), `at` (server clock, written as `w:date`). New items, suggestions and paragraph ids are minted from `id`, so every copy makes the same ids. Each kind of id has its own counter, so a paragraph keeps its id when an earlier application of the same change minted a different number of suggestions.

Validation (shared by client and server): known `kind`; `part` in the room's story list; spaces and offsets that exist; text length, batch size and property count caps; property local names on an allowlist with bounded attributes; link targets through `sanitizeHref`; no XML strings.

Kinds past the first draft:

- `insert-tab` types a `w:tab`, and `insert-break` types a `w:br` with `break` set to `line`, `page` or `column`. A line break may carry `clear` (`left`, `right` or `all`), written as Word's text wrapping break (`w:type="textWrapping"` and `w:clear`). The elements are the ones the engine's `insertTab`, `insertHardBreak` and `insertPageBreak` build. A tab or a break never goes into a control's prompt; the matrix checks them against the engine.
- `mark-format` sets run properties on paragraph marks, named by their addresses: the engine's `setParagraphMarkProperties`, which the editor sends with a format that covers a paragraph's end (a whole paragraph, a cell's only paragraph, the last paragraph of a selection). A `format` over several paragraphs reaches only the marks between, so without this kind a bold on a whole last paragraph could not say the mark's part, and the list's version would drop it. The client sends it in the same suggestion as the format (`into`).
- `table-property` carries the engine's own table op (`op`: `setTableProperties`, `setTableRowHeight`, `setTableCellFill`, `setTableCellVerticalAlignment`, `setTableCellBorders`), not a property list. The containers are named by their open items: tables, rows, or the cells of one table, read as one selection. A property list cannot say what a border op over a selection says, and the editor sends the op itself. A cell op (fill, borders, vertical alignment) that names one cell of a vertical merge covers every cell of the merged cell, which Word draws as one and the engine requires whole (task 3.6).

- `retract` may carry `undo`: earlier change ids of the sender's own namespace (the validator refuses another namespace as `foreign-id`) whose edits of the sender's own pending words it takes back exactly, as the editor's undo of them does. Each copy reads what they did from the list: the items they took back show again with their own addresses and suggestion (`taken`), the units they added to the sender's earlier pending suggestions are taken back (`doc.added`, address ranges each edit noted: typed text, a tab, a break or a note reference, Enter's new mark and split container edges, a new note's items), and the formats they gave the sender's own pending words and the values they gave the sender's own pending controls come off (an `untracked` format or value record names its change). A `retract` that only undoes such edits names no suggestion; one that names neither is refused as `empty`. It is refused as `not-pending` while a suggestion that inserted an item it changes is decided (an item to show again, a unit to take back, words to take a format off): a decision is final, so no undo takes back words someone accepted or rejected. A party's is refused as `others_suggestions` while another person's pending change is on the words it would take back, as for any take-back.
- `revert` (task 6.7) is the organiser's undo and redo of their own direct edits: `suggestions` names suggestions that direct edits made and accepted at once, and `status` turns them `rejected` (undo) or `accepted` again (redo). A direct edit is a suggestion accepted at once, so its exact inverse is that status turn: addresses never change, and each unit, mark and record shows as it did before (typed text goes, deleted text shows again, Enter joins back, a join splits again, a format goes off with the property gone, not turned off). The model marks a direct edit's suggestion (`direct`), so a revert of a pending suggestion, or of one a decision accepted or rejected, even the organiser's own, is refused (`not-direct`); one of another author's is refused (`not-own-suggestion`), and one already turned (`stale-revert`). A status turn that would leave words before a block with no paragraph (another person's words in a paragraph a direct table added) has no exact inverse: the room does not move them, so the redo shows every unit where it was, and refuses the turn by name (`no-inverse`, detail `others-words`, `leavesLooseWords`), on the server and in the client alike; once a decision or the person's take-back takes those words away, the undo runs. The pending suggestions around the reverted items move up a version, so a decision on a card the revert changed is stale. Caps: the suggestion list is under `ORDERED_CHANGE_LIMITS.targets` (1000), as a take-back's. Policy: a party never sends it: the suggestions-only policy refuses it as a direct edit (`policy-direct`, reason `text`, detail `revert`). Why a new kind and not a format with the earlier properties or a deletion of the same text: a format cannot say "this property was not there" (Word's on/off properties inherit from styles), a deletion of typed text leaves a deletion on record, and neither can show a party's struck suggestion again as it was. A status turn says all of it exactly, in one change.
  - For the turn to be exact, a direct edit never changes a pending suggestion as that suggestion's author (task 9.12): it lays its own settled record on the units, as on base text. A direct deletion strikes another person's pending insertion, break or row with the organiser's own deletion; a direct format, mark format or paragraph property inside another person's pending insertion or on their new paragraph is the organiser's own accepted record over those units. The Word form is the same as the engine's tracking-off edit (the units hide; an accepted record draws as a plain property, with no change record). Taken back, the record goes off and the other person's suggestion shows exactly as it was. Decisions on that suggestion do not touch the organiser's record, so they give one result before and after the undo (the matrix's order checks pass). The rule is one line: `pendingOwn` answers nothing for a direct edit.
  - Text the organiser typed inside another person's pending insertion becomes part of that insertion (the engine's rule), also where two parts of it meet and anywhere in their new inline control, which one `w:ins` holds whole (`settle` in `edits/direct.ts`); its undo is a direct deletion of exactly those units, and its redo turns that deletion back. Her direct note there is their new note, as a load reads a note whose reference a suggestion inserts (`linkNewNotes`). A paste sits beside their insertion, as Word pastes. A comment's marker anyone puts in a pending new inline control is part of its insertion too (`joinPendingControls`: a new comment's markers and a reply's, which sit beside its parent's), as a fold loads it from that `w:ins`: a reject or a take-back of the control takes the marker with it, as the editor alone's reject does (Word evidence is still to come).

Apply (`applyOrderedChange`, the room's `applyChange`): an edit maps to one or more model edits, run in the caller's undo record with one id minter made from the change id; a take-back to the model's retract; a decision to status changes; a comment, a reply or a resolve to the model's comment writes (D15), which save writes to the comment parts. The author is the room's stamp, the date its clock, and `mode: 'edit'` makes a direct edit. A suggesting change is one suggestion: its later edits (a press on several paragraphs, rows or tables) join the first one's. `into` must name the sender's own pending suggestion, and a direct edit takes none. Every refusal is a named `OrderedRefusal` and the record takes back every write. A target that no longer shows (a joined paragraph, a rejected row) is refused with `hidden-target`.

Decision seen check (as the host's earlier rooms refuse a decision on a card that changed after the organiser looked at it): every suggestion has a `version` that every model write touching its items or labels moves up (inside the undo record, so a take-back moves it back). A `decide` change names the cards as the organiser saw them: `cards` is a list of `{ suggestions }`, and each card's `suggestions` is a list of `{ suggestion, version }`, one for each suggestion of the card (`orderedCardSeen` builds it from the organiser's copy). One card is a one-entry list; an Accept All or a Reject All is one change that names every card (one request for each card, all at once, overran the host server's queue of one connection, and the room decided none; so the rule is one request and one change, not batches). The check is per card, and every card is judged on the document before any status turns: a card whose version differs, or that holds another set of suggestions now, stays as it is, and every other card is decided. So one late keystroke of a party does not stop an Accept All, as the host's earlier rooms refuse a decision per card. A card the engine's own plan leaves stays too, with the engine's reason (`engine-refused`), so no copy decides what the editor alone refuses: every copy composes each part the cards are in and plans them with the engine's `planRevisionBatch`, which selects every item of the cards, as the decision takes them all. A card stays only when the plan leaves an item the editor decides with its dependencies (`decidedAsBatch`: a structural change, a part with moves, a format record over several sites); an item the editor resolves on its own sites is decided as the editor decides it. So a card of several suggestions that the editor alone decides item by item is decided too: a deletion over a paragraph mark whose paragraph holds the author's paragraph record, which the batch alone would not drop with the mark. An accept of a column deletion whose struck cells hold another pending record of its author is one (`incomplete-group`); whether Word decides it is not checked. A format record whose runs reach into a text insertion or deletion is not one: Word accepts or rejects a format change inside a deletion on its own, so the engine plans the record and the text change apart, in the editor alone and in a room (`visit` in `store/store/revision-batch.ts`). The engine once tied them in one group and refused both cards, also in the editor alone; Word evidence for this exact shape is still to take. The check costs one compose of each part: about 7 ms for a decision on 3,000 paragraphs. Every copy applies the same change to the same document, so every copy leaves the same cards, and the organiser's copy tells how many it left (a requested card still pending). Only a change that leaves every card is refused: `stale-decision`, or `not-pending` when its first card is decided already; the room answers `apply-refused` with that reason, and the organiser looks again. A suggestion no copy holds refuses the whole change (`unknown-suggestion`): no organiser saw it. A flat list of suggestions was rejected: it loses which suggestions formed one card, so a card that one of its suggestions left (taken back) would still be decided. `orderedDecidedCards` gives the cards a decision decides now (the host server logs them). Caps: at most `ORDERED_CHANGE_LIMITS.decisions` (7,500) suggestions in one decision, which with minted ids of 80 units stays under the client frame (`__tests__/protocol-codec.test.ts`); the largest contract measured has 2,246 suggestions. A decision costs what its cards hold: `orderedCardOf` finds each card from the suggestion's own items and their neighbours. Tests: `__tests__/decide-many.test.ts` (model and room) and `__tests__/client/editor-decide-many.test.ts` (two real editors, 320 cards: the host's request and the editor's own Accept All and Reject All are one change, one store change on each editor, no card left, and the save holds none).

### D7. Client (stage 1: no editor change)

- `gateOperations(ops, scope)` translates each supported `TreeDocOp` into changes, applies them to the local list inside an undo record, and queues them. An unsupported op, a translation failure or a refused apply returns a refusal code before the engine commits: `ordered-unsupported-op`, `ordered-refused` (with the reason in the detail).
- `gateOperations([], scope)` (opaque writes such as editor review writes) is refused with `ordered-opaque-write`. A write whose package edits each say what they do (`CollaborationGateContext.packageWrites`, `describedPackageEdit`) is carried by that meaning, before its ops: the editing API's document properties are a `setting` (Word records no change of them, so the organiser's only, last one wins), and a bookmark it deletes from a story it does not write in is a `bookmark` change of that story.
- After the engine commits, the client compares the touched paragraphs with the list's composed paragraphs and publishes the list's version where they differ.
- A remote change: take back pending changes (undo records, last first), apply the server's change, apply pending changes again (a pending change that no longer applies is refused and reported), compose the touched paragraphs, publish with `applyRemotePackage`.
- Undo and redo: a stack of the person's own changes. Undo emits a new change that takes back the person's own suggestion (`retract`), so it never touches other people's text. The organiser's direct edits are taken back and made again with `revert` (D6). Undo of a kind without an inverse is refused by name.
- Presence: `setLocalSelection` sends paragraph id and offset; remote selections come back the same way.

How stage 1 is built (`client/`, task 6), and why:

- One opener for the room server and every client: `openOrderedWordFile(bytes, { file })` reads the package with the engine's bounded reader, normalizes it as the editor normalizes a document it opens (every paragraph gets a valid `w14:paraId`; an empty prompt-bearing control shows its glossary prompt), and loads it under the file's number. The matrix checked the list against the editor's normalized package, so the list must be loaded from the same form, and the server must load the same form or the copies' paragraph ids differ. The host server must use it.
- The editor's paragraphs carry the list's node ids. On attach the client publishes the whole composed package; from then on every publish keeps the editor's tree equal to the list, so an op's `paragraphId` names a list paragraph (a loaded mark's space is `m:<file>:<node id>`, a minted paragraph's mark space is its node id). Before translating, the client checks that the editor's text of each paragraph a batch names equals the list's view text; otherwise offsets mean other units, and the batch is refused (`text-differs`).
- Supported ops: `insertText` (cut under the text cap, the pieces at one place), `deleteText`, `insertTab`, `insertHardBreak`, `insertPageBreak`, `setRunProperties`, `setParagraphMarkProperties` (the `mark-format` kind), `splitParagraph` (alone, or with its `setParagraphMarkRevision`; `tailStyleId` becomes a `paragraph-property` on the tail, null as the default paragraph style), `splitParagraphMany` (every place read before the first split: addresses do not move), `proposeParagraphMerge`, `joinParagraphs`, `setParagraphMarkRevision` `del`, `setParagraphProperties`, `setListLevel`, `setListNumbering`, `setParagraphTabStops`, the five table property ops, `insertTableRow`, `deleteTableRow`, `insertTable`, `setContentControlValue` (the editor's string form read by the control's type, as the engine reads it), `setHyperlinkTarget` to a bookmark, and `insertNote`. Every other op is refused as `ordered-unsupported-op` with the op's name, before anything applies. D13 lists every op, its state, its group and its party rule; the review ops (accept, reject, a new comment's markers) are translated since task 9.3 (D15).
- The engine's property ops replace a whole set; a change merges. They agree when the op names every property the run, mark or paragraph authors now, which the editor's presses do (a toggle off is `w:val="0"`). An op that leaves an authored property out takes it off, so the change names it too, as a removal (`{ localName, remove: true }`, no attributes or children), which a `format`, a `mark-format` and a `paragraph-property` change may hold and a style may not: a toggle off of one's own pending bold drops `w:b`, and Clear All Formatting takes a font, a size, a colour, a style, a paragraph's alignment, indents and list off, as the engine's ops do. A run whose style turns a property on gets the off value (`w:val="0"`) from the editor itself. A suggested format that gives a unit back the face it had before its pending format records, when the presser wrote the latest of them, cancels those records (the item's `cancelledFmts`): the engine drops the run's one change record then, so no card holds the unit (Underline pressed twice). Undo of that press, a `retract`, gives them back. Another author's record stays, as the engine keeps it. A paragraph press sends only the properties it changes, so the list and tabs the editor sends back unchanged are not written again.
- A batch's changes are one suggestion: the first suggesting change makes it, the others name it in `into`. Each change has its own undo record, so the room refuses and the client takes back exactly by change.
- The publish runs in a microtask after the commit (or in `flushPendingJournals`), never inside the gate: the editor applies its ops to the tree it computed them on. A change names the paragraphs it wrote by their marks' addresses (typing, a deletion or a format, a paragraph's own properties, Enter, a join, a decision on text or on a paragraph mark); the publisher (`publish-region.ts`) composes them with the paragraphs a split or a join made of them, out to the nearest paragraph on each side that the last package shows unchanged, and replaces exactly those nodes there; a region that ends at a paragraph the last package does not show yet (Enter, a join taken back) reaches the paragraph after it too, whose words moved up (found by the random sweep, seed 104). A change that can move a block edge (a table, rows, a note, a move, a control's value, a decision on a container), and a region that crosses a block edge, compose the whole story. A composed paragraph that says what the last package shows keeps that package's node, so the editor sees nothing new there. The paragraphs the engine's own commit touched are composed again too, so an engine difference never stays on screen; a paragraph the engine made under its own id (its half of a split) is not in the published package, so the publish, which then always goes out, takes it back. An admitted batch the editor did not commit is taken back. An admitted batch the editor commits inside a publish counts as any other commit: a host that reads the editor on each change (a React store hook reads `snapshot()`) lands a waiting key there, and the client once took that key back with no word (the live session lost a party's second key). A write the editor makes without asking the gate is reverted by the publish and reported (`ungated-write`).
- The caret: before a publish, each endpoint of the selection is read as a place of the list, and read back in the node ids of the list's version before the editor takes it (`remoteSelectionMove`). A host read during that apply (page geometry, review item positions) lays the pages out at once, and that layout must find the move: the move was set only after the apply, so after Enter the caret stayed on the engine's own new paragraph and every later key was refused as `out-of-step` (`client/editor-enter-host-read.test.ts`). A collapsed caret keeps to the unit before it, so text another person types at the caret goes after it and the person's next keystroke follows their own text; a range keeps what it covers. An endpoint in a paragraph the engine made under its own id takes the caret the batch leaves: after the text it typed, else where its last change leaves it. A second publish before the editor takes the first move carries the first move's result on.
- Undo: a step is one or more of the person's suggestions and the changes that made them; typing beside one's own text extends one suggestion, so a typing run is one step, as in Word. Undo sends one `retract`. A step keeps the editor commits it came in. When its last commit edited the person's own earlier pending words (took part of them back, typed into or over them, put a tab, a break, Enter or a note inside them, pasted inside them, formatted them, set a value in a control they put in: a `delete`, `join`, row or column deletion, `insert`, `insert-tab`, `insert-break`, `split`, `insert-note`, `format`, `mark-format` or `control-value`), its undo takes back that commit alone, as the editor's undo does: one `retract` of the suggestions the commit made (another person's words it struck or formatted) that names the commit's changes in `undo`. The step's earlier commits stay on the undo stack, and the commit goes to the redo stack. A format on one's own pending words is a record of their own suggestion with no change record (`untracked`), as the engine formats its own insertion, so its undo takes off the format and leaves the words. A value in one's own pending control is part of that suggestion too, with a value record that names its change, so its undo takes back the value and leaves the control, and the next undo takes back the control, as the editor's undo does. A later take-back of the whole suggestion forgets which change took an item back, so an `undo` never shows part of a suggestion that is gone. A step whose last change, a deletion, took back the step's suggestion whole with its records (one's own new column, with its lent widths) has nothing to show again: its undo makes the step's earlier changes again, as a redo does, and the deletion goes to the redo stack. Redo makes the step's changes again under new ids, with every space and suggestion an earlier change of the step minted renamed to its new id (`i:`, `k:`, `c:`, `x:`, `S:`), so the later changes name the units the earlier ones make again. A suggestion someone decided has no inverse: the undo of a step that holds one is refused as `no-inverse` (detail `decided`), and the step goes. So is the organiser's undo of words typed directly inside another person's insertion that was accepted since. When the decision reaches the room before the undo, the room refuses the `retract` (`not-pending`) and the copy takes it back; a room's refusal of one of the person's changes clears the redo steps, so a redo never makes the words a second time. `historySelection` is the selection before the step's first change.
- The organiser's direct edits (tasks 6.7, 9.12): a direct typing run is one step, as the editor alone groups it: the editor's undo group of its commits decides (`editor/typing-history.ts`: keys at one caret, ended by a pause of 1 s, 2 s of typing, a caret move or another edit), for direct changes as for suggestions (`client/history.ts` `recordCommit`); the room once joined every key at one caret into one step, with no pause ending it. Undo reads the inverse from the list as it is then (`undo-direct.ts`): the step's direct suggestions (`S:<change>.<k>`, accepted) turn `rejected` in one `revert`, and the units the step typed into another person's pending insertion (`i:<change>.<k>` under that person's suggestion) go by a direct deletion of exactly those units. Redo is the inverse of the undo's changes (the revert turned back, the deletion's own suggestion turned `rejected`), so the same units come back with every other person's suggestion around them as it is. Every direct step has this inverse (task 9.12); a step nothing of which shows any more (another person took back the insertion the organiser typed in) is spent without a change. A party's suggestion inside the text the undo takes back stays (it is that party's, not the organiser's); one at a place the room had already hidden when it came lands before the next unit that shows (D6).
- Reconnect and restart: `hello.last` is the last order number the client knows the room saved, not the last it applied. On `welcome` the client takes back its pending changes and the room's changes after that save (it keeps their undo records until `saved`), applies the room's catch-up, and applies its pending changes again; its own changes after the save become pending again and are sent, and the room answers the ones it still has by id. So a room that restarted behind the client (at 57 while the client holds 61) and one that did not are handled alike, and no history after a save can differ between copies. A `welcome` before the client's own save, or a room change that does not apply here, ends the session (`room-generation-changed`, `remote-apply-failed`) with the unsent changes kept. A pending change that throws something other than a refusal when it is applied again (a defect) does not end it: kept there, it threw again at each join, and the person could not come back without losing every unsent edit (found in an acceptance run). As the room does with `apply-failed`, the client takes it back and refuses it by name (`apply-failed`, the error's type in the detail), refuses the pending changes that need it as the model refuses them (`pending-refused`), sends the others, and stays `ready`; `onApplyError(error, change)` gives the host the error to log. A sent one stays pending until the room orders or refuses it, as any sent pending change does, so the room's order decides and the copies cannot differ. A throw while the list is composed for the editor sets `error` (`remote-apply-failed`, `compose: <type>`) as a refused publish does; the paragraphs stay named, so a later publish heals the session, and the editor's detach and `destroy` always complete, so the page can close the session and join again.
- Concurrent edits the room refuses are refused by name and taken back on the sender's copy: a range whose ends crossed (`invalid-range`), a change that joins a refused change's suggestion (`unknown-suggestion`), a target another change hid (`hidden-target`). Random sessions with two and three real editors and held-back frames check that every refusal is one of these and every copy ends equal to the room.
- Each session has its own change id namespace (the actor id and a random suffix): a counter that started again under an old namespace would repeat ids, and the room answers a repeated id with its first order number and applies nothing.
- Presence carries node ids, which every copy shares; the person's actor id and colour go in `data`, and the name is the one the room stamps.
- Transports: an in-process room (`OrderedLocalRoom`, the room core behind the protocol as the host server answers it, with frames delivered later) and a WebSocket transport over the host's own socket (`addEventListener`, text frames only, the frame cap), so it runs in a browser, in another window and on Node 24 (checked with Node 24.22.1's own `WebSocket`). Timers for reconnects are the host's, read where any window will do.
- The editor must be in suggesting mode for a party, which needs a review module (`reviewModule()` from `@docx-editor.dev/pro`; core's tests use a stub).
- One key press lays out only the paragraphs it touches (task 6.8). Three parts:
  - The editor's remote delta (`remotePackageDelta`, over `canonicalTreeDifference` in `store/package/ooxml-difference.ts`) names the paragraphs a received package changed in two more cases: node ids that changed only inside paragraphs that keep theirs (`text-local` when every renamed node and every difference is text flow or a run's formatting, `flow-structural` when a renamed node is a control, a link or a field, whose ids other caches keep), and a block container whose paragraph list changed while the blocks around kept their ids (a split, a join, a paragraph replaced under another id: `flow-structural`, with the created and deleted paragraph ids). A paragraph that moves past another one that stays, or between containers, stays wholesale. The Yjs session in `packages/pro` gets the same narrowing for a received split.
  - A local change's date is the room's clock as the copy reads it from its own changes' stamps (`room-clock.ts`: each confirmed change gives a one-second window for the gap between the clocks plus the trip; the gap is the middle of the windows the latest stamps share), and a pending change keeps that date when it is applied again. The room's confirmation then composes to what the editor shows, and publishes nothing. When the room's second differs (a slow trip), it publishes the one paragraph again.
  - Compose keeps a loaded run's node ids (its shell, text forms and face) only in the paragraph it was loaded in. After a split both halves hold the run, and each half is composed on its own: a second copy under the same ids gave the editor's tree two nodes with one id. Counts on a 19-page document of 150 paragraphs (`__tests__/client/editor-layout-cost.test.ts`; paragraphs broken into lines again at three moments: the typist's publish after the commit, the room's confirmation, and the other editor). Before, for a party: typing, Backspace and bold published `global` (a change to the whole document) on the typist's editor after the commit and again at the confirmation; Enter broke 5 paragraphs at each moment and a join 7, all `global`. For the organiser, every confirmation published again, and Enter and a join were `global` on both editors. After, for both: no moment is `global` and no confirmation publishes; typing, Backspace and bold break one paragraph at the publish and one on the other editor, Enter two and two, a join one and one. The engine's own commit is unchanged.

Stage 2 (later, one editor change): an optional session member lets the client apply local edits itself, so the engine's own tracked edit is skipped.

### D8. Protocol

WebSocket, JSON text frames, one message per frame, size-capped. Client to server: `hello` (room, file number, last order number, code version), `changes` (a batch), `presence`, `decide` (organiser). Comments come in `changes` like edits (D15); the earlier `marker` request message is gone (protocol 3 was never handed out, so the version stays 3). Media bytes do not travel on the socket: the host uploads them (D14). Server to client: `welcome` (file number, Word file location, changes after it, current order number, where media is read, the room's content-lock policy (D5 policy 6)), `changes` (ordered batch), `ack` (id to order number), `refuse` (id, code, detail), `saved` (order number), `presence` (the person the login gives that client: `person`), `reload` (reason). Each change in `welcome` and `changes` carries the room's stamp: `n`, `by` (the sender's person, `OrderedPerson`) and `at`. The protocol version is 3 (`ORDERED_PROTOCOL_VERSION`); version 2 stamped a name (`by` and presence's `author` were strings), and version 1 had the blob frames. A frame of another version is refused (`invalid-version`), and the room answers `reload` with the reason `version`. A version or file-number mismatch gives `reload`. A change made against an older Word file of the same room never applies: besides the file-number check in `hello`, the item spaces that load makes carry the file number (`b:<file>:<node id>`; load takes the number, and the room and every client load one file with the same number, so their addresses agree), so an address from an older file does not resolve in a newer one and the change is refused as `other-file`. Node ids are positions in the file, so without the number the same position in the next file would take the old address.

This is the central-authority pattern of `prosemirror-collab` (order numbers, clients apply their unconfirmed changes again on top), applied to the item list. Because addresses never change during a session, no operational transform functions are needed. Yjs, Hocuspocus, Automerge and Loro are not used: they merge without a central order and keep a second full document copy per browser, and the host server must check every change in order anyway. Server: Fastify 5 with `@fastify/websocket` (`ws`); authentication calls the host's API as before; presence keeps the earlier rules (own entries only, size cap).

### D9. Room core

`OrderedRoom` (neutral) holds the list and the order. `submit(actor, batch)`: validate, check the policy, skip ids already applied (answer with their order numbers), apply each change inside an undo record (a throw takes it back and refuses it), assign `n`, stamp `by` with the actor's person (`OrderedActor.person`, checked and trimmed; a client may not send `n`, `by` or `at`: `server-field`) and `at`, return the accepted changes for the log and the broadcast. The apply context carries the person (`OrderedApplyContext.person`), and everything that builds an attribution from it sets both `author` (the Word name) and `person` (`OrderedAttribution`). One namespace belongs to one person ID: a change from another person on a namespace in use is refused (`stamp`), and a log that does so does not open (`log-stamp`); the same person under a new name or company keeps the namespace, and later items carry the new Word name. Own and other compare person IDs everywhere in the policy and the apply (`sameMaker`); a file's item has no person and is another person's for every sender. Validation is per batch: one malformed change refuses the whole batch, because only a broken or hostile client sends one (a correct client runs the same validator first). The policy and the apply are per change, all or nothing for each change: a batch is a burst of keys, not one intention, and the client takes back exactly the changes the room refuses by id. A change that depends on a refused one fails on its own targets and is refused by name too. The clock is read once per batch, before anything applies. Every copy applies the same lock rules (D5 policy 6): a change that a content control's lock forbids is refused by name (`locked`) for the organiser and a party alike, whatever a client sends. The policy is an interface; `suggestionsOnlyPolicy` implements the contract host's rule: a party may only add suggestions, change or retract their own suggestions, and write comments; no header or footer changes; no change inside another person's suggestion; no decisions. Comments (D15) have their own rules, for everyone: only a person the login gives comments (`OrderedActor.comments`, which the host sets only while comments are open) writes them, else `policy-comment` (`comments`); none in a header or a footer (`policy-furniture`, `furniture`); only the organiser resolves (`policy-comment`, `resolve`); a resolved thread takes no reply and no resolve (`policy-comment`, `resolved`); a document holds at most 5,000 comments, the Word file's counted, so a new thread, a reply or a note past that is refused (`policy-comment`, `limit`). A comment may cover another person's pending suggestion, struck text or a prompt (discussing a suggestion is the main use): it is no edit and never nested. Every sender comments in a batch of changes; there is no request path, because the room stamps the person. Its verdict equals the host's earlier check for every party change, except the check's own faults of Word form listed below. A policy may give a second verdict once the change applied (`checkApplied`, on the apply's outcome: the suggestions it made, extended or took back, and the records it took over); a refusal there takes the change back in its undo record. The suggestions-only policy uses it for what today's check reads from the result: a party's direct edit, and a party's change in a header or a footer, pass only when they make no suggestion (a deletion of a prompt, a format press that changes no value, an object property the object has already, a watermark removal with no watermark), for every change kind, as today's check finds no part changed; the engine makes no suggestion for an edit that changes nothing. A party's format that writes a record in a run of another person's pending insertion or deletion is nested (`policy-nested`, `nested`, `appliedNested`): only the outcome shows whether it wrote one, so a format the words have already passes. A party's format or property change may not take over another person's record (policy 2). A party's direct edit that types inside a pending insertion, the party's own too (inside one of its runs, anywhere in a row, a note or a text box it made, or in a control or a link it made), is refused before it applies, as direct typing in the file's own text is (`policy-direct`, `text` or `package`): the engine types it into that insertion as its author's, as Word extends a tracked insertion with untracked typing, so it makes no suggestion for the result to show (found in the multi-party acceptance run, a direct insertion in a control another party made). A party's page sends a suggestion there. The organiser's direct words there still join the insertion. So do the words of a value the organiser sets in a control a pending insertion put in (`control-value`, the Word file and a fold read them as part of the insertion's `w:ins`), so a reject takes the control with its value, live as after a fold. The strike of the old words and the control's record stay the organiser's own settled edit, and the units the edit added to the insertion are noted (`doc.added`), so the undo takes the value back exactly: the record reverted, the new words by a direct deletion. Before, the value was settled text of its own in the control, and a reject live left it as plain text where the file gave the words back. A party's take-back of their own pending items (a deletion over them, a join of their own new mark, or a `retract`) is refused (`policy-not-own`, `others_suggestions`) while another person's pending deletion, format or property change is on those items: the take-back would shrink that suggestion or leave it with nothing. Today's check refuses it too, because it keeps such a record as it stood when it rejects the party's own suggestions (found in the real-editor cell s2-short:1000, round 15). The organiser stays free to do it.

"Inside" reads what the change does, not only its address: typed words are judged where the engine puts them (past struck text); a control value and a new link target by the words they strike; a column change by every row it cuts through; Enter by the pending records it copies (another person's pending paragraph or mark format would go to the new paragraph under their name); a caret is inside another person's insertion where Word nests the new run in it: between two of its units (one run of theirs), in a row, a cell, a table, a note, a text box or a block control it made around the caret's paragraph, or in a control or a link it made, whatever the words there are (words of another suggestion, or words a decision accepted), but not beside their new paragraph mark, in the part of a link or a control that their Enter split off (Word marks only the new paragraph mark, so that part is in no insertion of theirs), past a link's or a control's end, at a link's or a control's start, where the engine types beside it as the editor alone does (judged once applied, so typing the keyboard sends into a control at its edge is inside it), or between their deletion and their insertion; a format is inside another person's insertion or deletion where it writes a record in a run of their `w:ins` or `w:del` (their words, a control, a link or a note reference they inserted, either end of their move, also a Word file's own revision): Word nests the record there, and today's check cannot take it back alone (it counts a change record's depth in content revision marks, and refuses one of the party's deeper than another person's mark it overlaps). ### D10. Persistence (host server)

Per room in S3: `room.json` (Word file number, writer number, code version), `file-<k>.docx`, `file-<k>.changes.zst`.

- Local log: one zstd stream per room. For each batch: write, flush, fsync, then broadcast.
- Upload: about every 2 s when changed, the whole log object up to the last broadcast batch, one upload at a time, `If-Match` on the previous ETag. Then send `saved`.
- Close: 60 s after the last person leaves, compose the Word file, write `file-<k+1>.docx`, point `room.json` to it with `If-Match`, delete the old log.
- Restart: read `room.json`, the Word file, and the longer of the local and S3 logs; check the order numbers have no gap or refuse to open.
- Fencing: a new process increases the writer number and rewrites the log once; the old process's next upload fails and it closes its connections.
- Join: a browser builds its tree from the Word file and the changes after it.
- Clients keep undo records until `saved`; after a restart they go back to the server's order number and send their own changes again.

### D14. Parts outside the story text (task 9.2)

Edits add to Word parts outside the story text: a picture's media part and its relationship, a link's external relationship, a new list definition, a new style, a new header or footer part, and a settings write. The ordered document holds each one as a resource in `doc.resources.added`, keyed by `p:<change>.<k>` from the change's id minter (`resource()`), with the suggestion that added it. Nothing is removed during a room session, as for items (D1).

- **Kinds.** `media` (a part named by the bytes' SHA-256, a content type from the engine's image list or a part kept as bytes and never opened: a chart's workbook, an embedded object's part, an ink part (D18), a size); `story` (a new header or footer part, whose story is in `doc.stories` through `addOrderedStory`, inside the undo record); `relationship` (from a story part to a resource of the same suggestion, or for a link to an address that `sanitizeHref` keeps as it is); `list` (a `w:abstractNum` and its `w:num`, as typed levels); `style` (a typed style, with run and paragraph properties on the allowlists); `setting` (the engine's own settings op, or the core document properties by name, replayed at compose). `custom-xml` (a custom node's payload, a data chip's data: the node its control's `w:dataBinding` names in the custom XML store of the binding's namespace, carried in the `insert-control` change that makes the control; the editor commits the custom node write through the gate with its package, so the translator reads the node from it; the store is the file's, or a new one under the `ds:itemID` the binding quotes; a store id that is not the namespace's store, or a node id another shown control binds (two people who each minted `cx1`), is refused as `name-taken`). A notes part when the file has none is group 9.9's: it uses the same `story` and `relationship` kinds, with the notes' separators. It is written while the list holds its story, not only while a note shows: once its last note goes (a deletion, an undo, a take-back or a reject), it stays with its separators, as Word keeps a notes part and as the editor alone keeps the part `ensureNotesPart` made. So every copy, the editor and a save and reopen hold the same parts.
- **Names.** Every Word name is a function of the key: the relationship id `rO<namespace>_<counter>_<k>`, the media part `/word/media/ordered_<token>.<ext>`, the story part `/word/<role>_<token>.xml`, and the list numbers by FNV-1a of the key. So every copy adds the same part under the same name, in any arrival order. Load records the file's part names, relationship ids by owner and list numbers. A resource that would take one of them, or another resource's name, is refused (`name-taken`) on every copy alike. Two style resources may name one style id: compose writes the first by key, and none when the file has the style.
- **Order.** Compose writes resources sorted by key, so two copies that applied the same additions in another order write the same package (`__tests__/resources-compose.test.ts`). Settings keep the room's order: Word records no settings change as a suggestion, so only the organiser's direct edits make them, and the last one wins.
- **Used only by its suggestion.** An edit may use a resource its own suggestion added, or one whose suggestion is accepted. Another person's pending resource is refused (`foreign-resource`), so a reject of the one never breaks the other. A list number a change added is usable by its author's later edits and, once accepted, by everyone.
- **What compose writes.** A resource is written while its suggestion is pending or accepted, and something written uses it. Compose starts from the loaded stories and follows the relationships whose ids a written part uses (`r:id`, `r:embed`, any attribute in the relationships namespace): their media parts and new story parts are written, and a new story part's own relationships are read in turn. A style is written when a written story names it (`w:pStyle`, `w:rStyle`, `w:tblStyle`) or a written style draws on it (`w:basedOn`, `w:next`, `w:link`). A list is written when a written story or style names its number. A settings write is replayed when its suggestion is accepted. A custom node's payload is written while a written control binds its node, the last one a change added for a node winning, as the engine's update replaces the node; a node of a file store that the loaded stories bound and no written control binds goes, as the engine's removal takes it. So a reject, a take-back, and a deletion of the content that used a resource all take it out of the file. A link's address is the one exception: a decision keeps a rejected new link that still holds something (a comment's start, a bookmark, another person's text), as Word's Reject All does, so its address stays while a written link names it (D19); it goes with the link element. The close (`composeOrderedPackage`) removes added parts that nothing uses. What each block uses is cached by the block's node, so a publish reads only the blocks that changed. Elements are built from typed values with the engine's builders; no XML string from a change is read.
- **One zip writer.** `orderedPackageBytes` and `writeOrderedPackage` share the engine's zip writer: `ZipEntryWriter` (`store/package/zip-write.ts`) writes one entry at a time and keeps only each entry's header fields; `writeZipSteps` collects its entries into one archive, and `zipPartWriter` (`store/package/zip.ts`) hands each entry on. The streaming writer composes each added picture as an empty part and reads its bytes by part name when the entry is written, so the composed package never holds an added picture.
- **Validation.** `change/resources.ts` bounds every field a change gives: the SHA-256 as 64 lower-case hex digits; the content type on the image list (a new picture's on the raster images the engine's picture commands write; a paste's on every media type, D18); the size up to 25 MiB, an SVG's up to 2 MiB (`ORDERED_RESOURCE_LIMITS.svgSize`: an SVG is parsed whole, so it stays small; `orderedMediaCap` in `change/resources.ts`); list levels in order from 0, at most nine, the start up to 32767, indents up to 22 inches, the number format on an allowlist, the level text up to 32 characters with no control characters; a style id pattern and a font name pattern; style properties on the run and paragraph allowlists; the settings op on an allowlist. The readers refuse `__proto__`, `constructor` and `prototype` as keys, as every reader does.
- **Media bytes never travel inside a change, nor on the room's socket.** A change names media by its SHA-256. The host stores the bytes first, once, through the session's `upload` option (`OrderedMediaUploader`, beside `media`): `upload({ location, sha256, contentType, bytes, signal })`, where `location` is `welcome.blobs` (the place media reads come from; the host appends the hash) and `signal` aborts when the session ends. It answers `{ stored: true }`, or `{ stored: false, code }` with `blob-too-large`, `blob-hash`, `blob-type` or `blob-quota` (`OrderedBlobRefusalCode`); a rejected promise, or any other answer, is a transient failure. A change kind names the hashes it uses through its spec (`blobs`). The room refuses a change whose media its storage does not hold, as `missing-blob`, before the policy runs. `welcome` names where clients read and store media: `blobs`, a location the hash is appended to. The client reads the bytes from there, by hash, before it publishes the picture (group 9.4). Until the bytes arrive, the screen leaves the media part and its relationship out (`missing: 'skip'`); a save refuses (`missing-blob`).
- **Storage contract for the host server.** The server:
  1. Serves the upload: `PUT <welcome.blobs><sha256>` with the person's token, `Content-Type` the media type and `Content-Length` the size, only for people the host's API admits to the room as writers. It answers `200 {"stored": true}`, or a 4xx with `message_code` set to a refusal code. An answer the host takes as transient (`read-only`, `room_not_open`, `not_authenticated`) makes the page try again later.
  2. Checks the size (at most 25 MiB, an SVG at most 2 MiB), the bytes against the content type with `isOrderedMediaBytes`, and the SHA-256 of the whole bytes with `orderedBlobHash`, then stores the blob content-addressed under its SHA-256 with a conditional write (`If-None-Match: *`), so a blob is written once and never changes. The storage path is the host's choice. A blob it already holds is answered `stored` at once.
  3. Caps the bytes per room (default 512 MiB) and per person (default 128 MiB), and the rate of uploads per person with the edit budget; past a cap it answers `blob-quota`.
  4. Passes `{ has: (sha256) => stored }` as the room core's `blobs` option, so `submit` refuses `missing-blob`.
  5. Serves `GET <blobs location><sha256>` only to people the host's API admits to the room, with the stored content type, `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` (an SVG is a document that can hold script; served this way, none runs) and `Cache-Control: private, immutable`. It never serves a hash outside the room's set.
  6. At the close, writes the room's next file with `writeOrderedCheckpoint(doc, base, { media, write })`, not with `writeOrderedPackage`: it holds no picture bytes, so a close no longer writes every picture again. The room's record names the file's format, and anything that reads the room's file directly gets a checkpoint. A real Word file comes only from `writeOrderedPackage(doc, base, { media, write })` (an export): the same bytes as `orderedPackageBytes(doc, base, { blobs })`, written front to back to `write` (each part when it is written, the central directory last; `write` is awaited, so a slow upload holds the writer back). Each picture, the file's own that a checkpoint names and each added one, is read through `media` (by SHA-256) when its part is written, one at a time, and is not kept after it. Both writers refuse a `media` rejection, or bytes of another size than the change or the manifest named, as `missing-blob`; the bytes already written are not a whole file, so the host stops the upload, and the log stays. After the new checkpoint is written, the server deletes only the blobs that it does not name, once no open session can name them: after the room's next open, from the checkpoint alone.
  7. Logs a blob's hash and size, never its bytes.

- **A check from the first bytes (`client/media-check.ts`).** A host that streams an upload to storage keeps the first `ORDERED_MEDIA_PREFIX` bytes (1 MiB) and calls `checkOrderedMediaPrefix(prefix, { contentType, size })`. The answer is `valid`, `invalid` or `whole`. `valid` means `isOrderedMediaBytes` passes on the whole file of that size, whatever bytes follow the prefix; `invalid` means it fails. The first bytes decide `invalid` only by a wrong signature, a size over the cap (0, over 25 MiB, an SVG over 2 MiB, or a prefix longer than the size), or an image header read inside them and over the engine's pixel caps. `whole` means only the whole file decides: the host runs `isOrderedMediaBytes` on the stored file. Rules:
  - When the prefix is the whole file, the answer is the whole check.
  - A prefix under 8 KiB of a larger file decides nothing (`whole`): every signature and fixed header the checks read lies in the first 8 KiB (an ink part's `<` the farthest, after at most 4,096 bytes of white space).
  - A zip (an embedded Office file, a chart's workbook), an OLE compound file and an ink part are decided by their signatures.
  - PNG, GIF, BMP, WebP, EMF and WMF headers lie at fixed places in the first bytes, so the prefix decides them. The EMF header record's size is measured against the file's size, not the prefix's.
  - A JPEG's frame header and a TIFF's first image directory lie where the file says. When the engine's reader (`validateJpegHeader`, `validateTiffHeader`) finds the header in the prefix, it finds the same one in the whole file, so the prefix decides; when it does not, the answer is `whole`, never `invalid`.
  - An SVG is `whole` unless the whole file is in the prefix: it is parsed whole.

  The check calls the engine's image checks on the prefix and reads their answers; it does not change them. Tests: `__tests__/media-prefix.test.ts` cuts real files of every type at every byte (PNG, JPEG with its frame header past 8 KiB, GIF, BMP, lossy and lossless WebP, two TIFFs whose first image directory is at the end, Word's EMF, a WMF, an SVG, a zip, an OLE part, an ink part) and holds every `valid` and `invalid` answer to the whole check with three different rests past the cut; files over the caps give `invalid` only once the header is in; a JPEG and a TIFF whose header lies past the first MiB give `whole` and pass whole.

- **Room checkpoints (`compose/checkpoint.ts`, `model/checkpoint.ts`, `model/file-media.ts`).** The file a room writes at each close is a checkpoint: the parts of the Word file that `writeOrderedPackage` writes for the same document, in the same order, without its media parts, and one manifest part, `/ordered-checkpoint.json`. The manifest is JSON: `format` (`docx-editor.dev/ordered-checkpoint`), `version` (5), `media`, one entry for each part left out: `part`, `sha256` (`orderedBlobHash`), `contentType`, `size`, and `entry`, the part's place among the Word file's entries (the zip order decides the bytes of the Word file), and the room facts Word has no place for, one section for each kind, each keyed by what the composed file writes and a load reads back (Word ids, a label), never by model addresses, because addresses hold the file number, and never by a count of places in the file, because a later engine may read one more element or unit than this one: `suggestions`, `comments`, `takeovers`, `namespaces`, `untracked` and `lists`. A suggestion keeps its id; a section that names a suggestion names it by its place in `suggestions`. Each element a fact names, and each element whose units a room change typed, carries an attribute of the checkpoint's own namespace (`CHECKPOINT_NAMESPACE`, `https://docx-editor.dev/ordered-checkpoint`, prefix `oc`). The content types and the relationships stay as they are. Word does not open a checkpoint.
  - **Suggestions and persons.** The Word file holds names only, and Word gives each part of one change its own `w:id` (a replacement's deletion and insertion, an insertion with a new paragraph mark, typing with a table or a control record), so the file alone does not say which marks are one suggestion. `suggestions` lists every pending suggestion once, in the order the room made them: `{ id, author, date, attributes, person, revisions, record, status, version, direct }`, its id, its attribution with the file's other attributes and its person (a field with no value, such as a file's own suggestion's person or a version of 0, is left out), `revisions`, every `w:id` the composed stories and the glossary write for its marks, every role (`revisionIdsOf`, kept when a story holds it), and `version`, the room's writes that touched it, which a decision names. `direct` marks a direct edit's suggestion whose records the manifest keeps (a table's, a row's or a cell's properties listed in `untracked`): a fold reads it as a direct edit again, so a reject of a pending row or cell record resets the row's cells that hold only direct records, as live and the editor alone do. A reader refuses it on a pending suggestion; an older reader refuses the field. The open's own steps give records back through model writes; after all of them it sets each suggestion's version to the listed one (absent is 0), so a fold changes no version and a decision that names what the room showed applies after it. It also lists a suggestion another section names that writes no mark (a control's value, a decided record of properties an untracked record changes), with its `status` when it is not pending. A load makes the listed suggestions first, in this order and under their ids (`OrderedLoadOptions.suggestions`, set only by `openOrderedCheckpoint`), so the room's order of creation is kept and every read that names suggestions (the cards, `orderedSuggestionsOfRevision`, `orderedReplacedSuggestions`, the records, `item.by`, `item.dels`) gives the same ids after a fold. An id the engine mints (`S<n>`) passes over every id the document holds (`newSuggestion`), and a change whose id the room ordered before the fold would make a suggestion the document holds: it is refused as `name-taken`, never a throw. A session on the older file is refused by the file number in `hello`, as before; a decision names no file, and no check relied on new ids. A change record of the styles part is listed too, with `record` (its local name) and its one `w:id`, so `loadPartRevisions` keeps its id; it is read as no mark of a story. A plain Word file gets new ids, and `OrderedRevisionIds.listed` keeps their ids in this order, by which open puts back what the other sections name; a mark whose `w:id`, author and date are those of a listed suggestion is read as that suggestion, whatever its role. A mark of no listed suggestion is the file's own, one suggestion for each revision triple, with no person. A prompt that content took the place of keeps its records in its glossary block, as the engine keeps it: the room keeps the prompt as the first fill drew it in the control's original (`change/settle-named-prompts.ts`), which compose keeps the block from; the load keeps each listed suggestion's ids (`OrderedRevisionIds.listed`), and when the control empties, the prompt's units read a listed mark as that suggestion again (`RevisionReader.forPrompt`), so its card comes back. While content fills the control, `isOrderedItemHidden` reads the room's prompt units as hidden, as the cards do (`isCardUnit`), so a fold, which keeps them in the glossary only, changes nothing it says. A load reads each change record of a glossary prompt as a suggestion, as it reads the stories' marks (`readPromptRecords`), so a reopened Word file keeps it too; when a decision empties the control, compose gives each record of the prompt it restores the engine's accept or reject by its suggestion's decision, and a pending one stays (`withPromptDecisions`). The editor alone gives the same (its Reject All restores the prompt with the pending record, and a second one takes it). Word for Mac shows the restored prompt without the block's direct formatting, with or without a record (2026-11-20, `~$prompt26.docx`): a difference of the engine's own restore. `comments` gives the person of each room comment: `{ id, person }`, by the comment's `w:id` (D15, `OrderedLoadOptions.commentPersons`). The values are untrusted: each person read by the person rule; each `w:id`, author, date and other attribute read as a load keeps them from a revision mark (`load/state.ts`: any text valid in XML, XML names, at most the load's 8 other attributes, none of the triple, none twice), so every value the room took from a file comes back; a comment id named once; every list and string inside the manifest's byte cap, with no smaller cap; a person whose Word name is not the author the file wrote for that mark or that comment does not fit. Either refusal is `checkpoint-manifest`. A manifest of an older version is refused as `checkpoint-version`: no room is deployed, so there is no migration. `writeOrderedPackage`, `orderedPackageBytes` and `composeOrderedPackage` never write any of these facts.
  - **Typers.** A room change that types inside another person's pending insertion joins it, as Word extends a tracked insertion with untracked typing, and its units' space names the change's namespace; a load makes new spaces. Direct typing in a pending new row, note or text box is part of it with no marker of its own (`quiet`), as Word writes it there and a load reads it back. Compose writes the change's namespace on the element each such unit is drawn in, for the checkpoint only (`oc:typer`): its run, each run of a field, or the unit itself when it is drawn bare (a simple field, an equation, an element kept whole). A run holds one typer's units: its key holds its items' `run`, and the units of one `run` are one change's (its `i:<change>` space) or one loaded element's, so a checkpoint and the Word file it stands for draw the same runs and open under the same addresses. Only a checkpoint's compose reads the typers. A load reads the units of a typed element under its node id (`OrderedItem.run`), so who typed each unit comes back with no count of units. `namespaces` gives the person of each namespace the parts name, `{ namespace, person }`: the document keeps the person of each namespace whose change it applied (`OrderedDocument.namespaces`, written inside the change's undo record), and the load puts back those the manifest names. `orderedUnitTyper(doc, item, offset)` names who typed a unit of a pending insertion (its own, or the innermost new row or cell around it) as an `OrderedTyper`, `{ namespace, person }`, from its space while the room runs and from the typed elements after a fold, so it answers the same. An `OrderedRoom` knows the owner of each namespace its document names from the start, so after a fold `namespaceOwner` answers and one namespace stays one person. A typer namespace that `namespaces` does not list, and a namespace named twice, are refused as `checkpoint-manifest`; a listed namespace no element names opens (compose may draw a part a save drops).
  - **Takeovers.** Word keeps one change record for each properties element, under the latest author (D5 policy 2), so the file alone loses the records a suggestion took from another. The manifest keeps them: `takeovers`, one entry for each change record that holds records by takeover, `{ label, taken }`, by the label on the change record (`rPrChange`, `pPrChange`, ...), never by model addresses or places; `taken` lists each record it took, in the order compose draws them, as `{ suggestion, properties }`: an index into `suggestions` and the properties element with that record (`w:rPr`, `w:pPr`, `w:sectPr`, ...) as XML. Compose notes each takeover where it draws a pending change record (`ComposeContext.takeovers`, by the record's node id, carried to a copy that `fresh` makes), and the writer labels those change records in the composed parts. A record taken from a suggestion decided since takes over nothing (`orderedReplacedSuggestions` leaves it out), but the room keeps it apart from its suggestion's own record, so the manifest keeps it too: else the file's one change record loads as one record, and the open refuses the change records' facts of two. A text box whose story holds a takeover is drawn from its story, never kept in the file's form, which lacks the change record compose drew. `openOrderedCheckpoint` puts them back after the load (`client/takeovers.ts`), each by its listed suggestion; each loaded record that holds the change record (a format's face record, a property's element record, a field's run) gets the taken records in front of it, held by its suggestion, with `replaced`, its seq, and the properties as a face or an element record; each run of a field keeps its own face under each taken record, as a load gives a field's runs theirs. The values are untrusted: the manifest's byte cap, each properties element read by the engine's bounded XML reader and checked to be the element its record names, no label named twice; a takeover that does not read, or whose label is on no change record a loaded record of those properties holds, or on two, is refused as `checkpoint-manifest`. A table, a row or a cell is never taken over in a room: the engine refuses a change of one that holds another author's pending property change (`other-authors-row-change`). The exports and the composed Word bytes of a checkpoint do not change. A takeover of a takeover keeps every earlier link: the record's `replacedEarlier` (oldest first) beside `replaced`, and in the manifest the optional `earlier` of a taken record and `replacedEarlier` of an untracked record, by their places in the list (version 5 stays). A load that joins the pieces of one room run again takes one record for two only when both were taken from the same suggestions in the same order (`sameTakenFrom`): before, a piece's record taken from two suggestions became its first piece's record taken from the second alone (found by the fold shapes session, seed 87; `__tests__/checkpoint-fold-decide.test.ts`). A take-back gives the record to the latest suggestion it was taken from that is still pending (`recordsWithout`, `edits/retract.ts`), so Ana's record that Ben took and Olive took from Ben goes back to Ana once Olive and Ben take theirs back, live and after a fold (`__tests__/checkpoint-fold-decide.test.ts`).
  - **Untracked records.** A record shown with no change record (`untracked`: a control's value in `w:sdtPr`, a column's lent width in `w:tblGrid` and `w:tcPr`, a row's height Word adds with no record) keeps the old properties only in the room, and other records of the same properties hold what it gives (a pending cell change's record holds the lent width in its old properties; a direct value given later shows over a pending one). `untracked` keeps, for each properties element of a table, a row, a cell or a control that a pending untracked record changes, or that holds a record made over a pending one (a direct table or cell write, which Word's one change record holds as the pending record's): `{ label, target, properties, records }`, by the label on the container (`w:tbl`, `w:tr`, `w:tc` or `w:sdt`), the container's own properties of that element, and every record of them, decided or not, in the order they were made (a record taken from another too, which its change record also holds), as the room has them (`{ suggestion, element, untracked, merge, recordUnchanged, tableCells, replaced }`, the cells by their labels; `replaced` names the suggestion an untracked record took the record from, as no change record holds that takeover; `over` names the pending records a direct record was made over, so their reject takes it away after a fold as live: a direct column beside a new cell, over a row height's grid record; on a column's lent width or grid it names the pending records it was lent over, so their reject keeps it lent after a fold as live, and a lent grid's `element` keeps their original as the engine split it in its `w:tblGridChange`). `openOrderedCheckpoint` puts them back (`client/untracked.ts`): the container's own properties are the manifest's again (only the children the records set, when every record sets some; none, when the container had none and the file's held only what the records give), and the manifest's records take the place of those loaded from the file, each with a new seq in the manifest's order, so compose draws them over those properties as the room did and a decision after a fold gives the same file as one without. A record made after another keeps drawing on top of it when its suggestion is the older one (a height on its author's own new row after another person's height, a direct height after a record another took). A record taken from another that the manifest does not list (a checkpoint written before it listed them) stays as the takeover put it back, in front of the record that took it. The other untracked writers need nothing: a format on its author's own pending words, a press on its author's own new paragraph and a section break's type on its author's own new mark belong to an insertion that a reject takes away whole; a section type Word writes untracked is kept by a reject either way. A label on no container the load holds whose properties the target is (a cell for `tableCells`), or on two, is refused as `checkpoint-manifest`.
  - **Change records.** A pending record of a table's, a row's or a cell's properties that Word's change record holds keeps room facts the record does not say: a table op records each cell it does not change and sets nothing there (`merge`), and notes the cells the table showed (`tableCells`), which a decision on a column reads (`holdsCell`). Word's record gives the whole properties and no cells, so a reject of a column after a fold would keep the widths the column lent. `changeRecords` keeps each such record the untracked section does not list (a suggestion's records of one target that hold no takeover, which a take-back can give back to it, as one: the last, setting every child they set, as Word's one change record loads), by the label on its container and its target, `{ label, target, records }`, each record as `{ suggestion, replaced, merge, tableCells }`, the cells by their labels. `openOrderedCheckpoint` gives them back after the takeovers (`client/untracked.ts`), each to the record the file loaded of that target with that suggestion and the one it was taken from, in their order on the container. Load keeps a change record's old properties as the container's own, so they are the nodes of the file's record; compose writes the file's record back only while nothing made later changed its original (a column made after the load lends a width from it, or adds to its grid): then the record takes copies of the original compose draws, as after another fold; a record that sets only some children shows those, and compose writes it a change record of copies, as a room's record has, never the file's record (`fileRecordAlone`). A direct change made over such a record (the organiser's column over a party's row height) shows in Word's change record and in no room record, so the record that holds the file's change record sets the children where the file's properties differ from the container's own too (`changedKeys`). A label on no container or cell the load holds, or a record the file did not load, is refused as `checkpoint-manifest`. A reader of an older engine skips `changeRecords` and reads each record as Word's change record says.
  - **Made-over records.** A record with no change record of its own made over a pending one (`over`: a direct format, paragraph press or section write, or a format on its author's own new words or a press on their own new paragraph) shows in Word's one change record, which holds the properties before the first pending record, so a load read it as part of the pending suggestion's record: a take-back of that record after a fold took the write away, while live keeps it, as a take-back never touches another person's work; and a pending change made after it shows on top of it, which one record of the file cannot say. `madeOver` keeps, for each such `w:rPrChange`, `w:pPrChange` and `w:sectPrChange`, by the label on it, `{ label, target, records }`: every record compose draws from the first pending one (`madeOverDrawn`), in the order they apply, as the room holds it, as `untracked` keeps a container's (`readPropertyRecord`): `{ suggestion, replaced, replacedEarlier, over, untracked, keptOnReject, format | paragraphOp | sectionOp }`, a write read with the readers of the change that makes it (`model/checkpoint-over.ts`), or the properties a record a load read gives (`element`, with `merge` and `recordUnchanged`). The takeovers section leaves such a change record out. `openOrderedCheckpoint` puts them back after the takeovers (`client/made-over.ts`): on each item whose loaded record holds the change record, the manifest's records take the place of its records of those properties, each with a new order after every record of the document, so compose draws them as the room did; each record that gives properties, as a load reads one (also one another suggestion took over), keeps the file's change record, which states the properties before it, as the record a load read does. The section is left out when it has no entry, so version 5 and the golden checkpoints stay. A label on no change record of its target that a loaded record holds, or on two, a suggestion not listed, a record on its own new words of a direct edit or of a rejected suggestion (a decision of the new words decides it, so it may be accepted), a direct record of no accepted direct edit, another target's write, a write beside an element, or a write that does not read as the room writes it, is refused as `checkpoint-manifest` (`__tests__/checkpoint-fold-over.test.ts`).
  - **Prompts and value records.** A prompt a suggestion's content hid is written in the glossary with its change records, each under its suggestion's decision, as the prompt shows again (`withDecidedPrompts`): a decided record is no suggestion a load reads again (`__tests__/prompt-records-fold.test.ts`). The prompt keeps the containers that hold its words, as the editor alone keeps the control's content whole: the organiser's link on a prompt's words is in the glossary block, its relationship is written while the block names it, and the prompt shown again from the block holds the link, live and after a fold. Relationship ids are per part (OPC): the glossary holds its own copy of each relationship a kept prompt names, under the same id, so the block resolves in the glossary and again where the prompt shows (`withPromptRelationships`, which the room calls once its own relationships are written), and the glossary's root binds each prefix the block uses (`r` on a link), as the editor alone writes it. A control's own record of its value (`w:lastValue`, `w:fullDate`, `w14:checked`) is the engine's: typing over a prompt writes none, a pick writes the item's, and a decision that shows the prompt again reads it back from the prompt, so a fold writes no value a later reject keeps (`client/editor-controls-value-fold.test.ts`). A decision reaches the record only through units that read as the control's text, as the engine reads it (`contentControlTextOf`): a rejected field with no result keeps the value, live as after a fold. A reject of typing over the prompt keeps a record its words do not state (`recordStatesText`): the value the file stores beside its prompt stays, in the editor alone, live and after a fold. A decision that takes a pick or struck words away clears the record. A value proposed over words that do not read back to the record the control stores (a prompt, or a date in a format that does not show all of it, such as `MMMM yyyy`) keeps that record while it is pending (`proposedProperties`, the room's `setControlValue` too): the reject gives it back, and the accept reads the new one from the words (`newWordsBesideRecord`, the room's `filled` read-back). A record that shows as the words states them, and a field the format does not show reads as its first value (`statedValue`, `parseContentControlDate`). Accepted trade-off: a file holds one record, so the accept of a value whose format does not show a field (`MMMM yyyy`) reads that field as its first value (the 1st of the month, not the picked day); the shown text is the same, and Word evidence for what Word keeps there is pending. Block controls follow the same rule as inline ones: one `noteValueRecord` reads what their units tell (`ValueSigns`) for both. A record whose direct edit was undone is no value record the control follows (`valued`). Words a direct deletion took are no words a decision takes away, whatever is decided on their insertion (`decidedAway`): a fold keeps none of them, so a reject of the picks they cut keeps the value the file stores beside its prompt, live as after a fold. Words that state no value keep the record, but for one that the inserted words a reject took away stated: it goes (the engine's `stale`, the room's `ComposeContext.stale`), and the room reads every list and date record with the engine's `valueRecordEdits`. A pick of the value the prompt stores, rejected, clears it as the engine does: the file cannot tell that value from the pick's, so a kept prompt shown again reads its record back too (`readsRecordBack`, `readValueBack` in `change/settle-named-prompts.ts`). Words whose insertion was taken back never were, so they are no words that went, for a kept prompt and for one a fold put in the glossary alike (`takeWent`, `scanControl`): another person's value over the pick, taken back after a fold, leaves the pick's reject reading the record back (`__tests__/checkpoint-fold-prompts.test.ts`). A control those words alone filled is empty all the same, as compose finds it (`closeBox`): typing over a prompt, taken back after a fold that kept the prompt in the glossary only, shows the prompt again as live (`Went.takenBack`). A comment that ends inside a prompt a fold keeps in the glossary ends there again when the prompt shows again, as the engine restores the block whole: the prompt's units keep a comment's marker its range lacks (`lackedMarker`), and never one of a comment the file does not hold. Nor are they words a reject took away (`ComposeContext.rejectedWords`): a pick whose author took part of it back, rejected beside another person's words, keeps the record its words left no longer state, as the engine reads the file (`__tests__/checkpoint-fold-decide.test.ts`). A fill taken back was no first fill either: the next fill keeps the prompt as it shows then, with a format suggested on it (`kept` in `change/settle-named-prompts.ts`), as the editor alone, whose undo takes the first fill's glossary block back. A prompt that shows again goes where the engine puts a value (`withValueRun`): before the range ends and comment anchors that close the control's content, so a comment made on the words that filled it keeps its range around the prompt (`promptPlace`, for a new prompt and for a kept one that a marker stands before; `client/editor-controls-value-fold.test.ts`). The units a kept prompt takes there are read back as a glossary prompt is: each change record is its suggestion's by the `w:id` the room wrote for its role, also before any fold (`RevisionReader.forPrompt` with `suggestionOfRevision`), so a format suggested on the prompt stays its suggestion's. A format on the prompt taken back while content fills the control comes off the kept prompt too (`formatTakenOff`), so a fold writes no record that never was. A control in an emptied control that shows its value or its prompt is content, as the engine reads it (`holdsContent`): the outer control shows no prompt beside it, live as after a fold (`takeWent`; `client/editor-controls-prompt-nested.test.ts`). A prompt given back as items keeps a control it holds whole, marked as a load marks a prompt (`promptUnits`, `markPrompt`): a reject after a fold shows the combo box in the prompt again, not its words alone. A block prompt of two or more paragraphs given back as items keeps each paragraph: each mark but the last is the prompt's, and the control's shown mark becomes its last (`promptUnits`, `promptParagraphEnd`), as a load marks them, so typing in one paragraph replaces the whole prompt.
  - **Room runs.** Compose draws units of one `run`, one face and the same format records as one run, and text of one text form as one text element; a format record that no longer shows (rejected, or a direct one a reject took away) splits no run (`drawnFormats`). A pending suggestion splits such a run into pieces, and a load reads each piece as a run of its own, so a decision that takes the suggestion away would draw two runs where the room draws one. For the checkpoint only, compose numbers each run it draws from units and each of its text elements by the room's run, face and text form, not by its format records, which the file draws (`oc:run`, a number unique in the checkpoint), not by the paragraph it is drawn in, so the pieces a pending paragraph break makes share a number and counts the elements of each number; the label walk keeps a number only where more than one element carries it, as one alone joins nothing, and drops the namespace from a part left with none. An open joins the pieces of one number again after the takeovers (`client/room-runs.ts`): the first piece's run and the paragraph it was loaded in (`home`: a piece after a paragraph break is drawn with new ids, as in the room), and its face, format records and text shell where the others say the same.   - **Properties drawn for records.** Compose draws a `w:rPr` for a run or a paragraph mark, or a `w:pPr` for a paragraph mark, where the item has none only to hold a change record (a format record, a mark's `w:ins` or `w:del`, a paragraph change record); a load reads such a container as the item's own, so after a fold a decision that takes the record away wrote an empty `<w:pPr/>` or `<w:rPr/>` where the room writes none. A checkpoint with no mark reads as before, and a reader of an older engine drops the attribute as every attribute of the namespace.

  - **Styles.** A style a change added (a paste's own, a link's or a list's) is written the same way, in the styles part, while a story names it and the file has none with its id. `styles` names each one compose drew, `{ suggestion, key, styleId }`; an open takes the `w:style` out of the styles part before the load, with a styles part that holds nothing else, and gives it back to its suggestion as a whole style (`styleElementResource`, as a paste holds one). A level the loaded file declares is the file's and is not listed. A relationships part left with none goes, as the room wrote it only for them. Each comes back to its suggestion by the rule the lists and styles share (`withCheckpointGiven`), so a decision after a fold writes or leaves it out as the room does live (`__tests__/checkpoint-fold-resources.test.ts`). A reader of an older engine skips `resources` and reads them as the file's.
  - **Labels, and the tolerant reader.** The writer puts the labels on after compose, in one walk that makes again only the paths it changes: `oc:label`, a number unique in the checkpoint, on each element a takeover, an untracked record, a change record or a made-over record names (`model/checkpoint-labels.ts`), and the namespace declared on the root of each part that holds a label, a typer or a room run's number. Properties the manifest holds as XML (a takeover's, an untracked record's) declare each prefix they use, so a read gives back the prefixes of the part they came from. A text box's legacy copy takes the labels of its story when the package is written. Every open (`openOrderedCheckpoint`, `openOrderedWordFile`, `openOrderedRoomFile`) takes each attribute and declaration of the namespace off in one walk over every part, after the editor's normalization and before the load, and gives back what it found: a Word file drops it, so an upload brings no label or typer into a room, and a crafted upload cannot make the room's next checkpoint unreadable. A label is never read as a count. The copy the load reads decides: an entry's label must be on one element of the kind it needs that the load holds; a copy elsewhere moves no fact. The manifest reader adds, never changes: it skips a section and a field it does not know, stays strict on the type and value of every field it knows, requires every section of its version, and refuses `__proto__`, `constructor` and `prototype` anywhere (one JSON reviver). Changes from clients stay strict. The version moves only for a change an older reader would misread. Golden checkpoints of version 5, with their fold prints (`__tests__/fixtures/checkpoints/`, `__tests__/checkpoint-golden.test.ts`), must open to the same print in every later engine.
  - **A field's face.** A load reads a whole field's face from the run a format reaches (the outer field's first result run that holds a text, a tab or a break, else its own separator's run, else its begin run, never a run of a field nested in it: `formatRunsOf`, the engine's `formatRunIds`), as compose writes a format there, so a direct format on a field reads the same after a fold.
  - **Which parts become references.** A part whose content type is an `OrderedMediaType` that the package reader keeps as bytes, with at least one byte: pictures, a chart's workbook, an embedded Office file, an OLE object. An ink part stays inside: the package reader reads `application/inkml+xml` as XML, so it is a tree in the Word file. A part the package root relates (the thumbnail, often `image/jpeg`) stays inside, and so do fonts, printer settings, `.wdp` and every other type. `orderedPackageMedia(pkg)` lists the parts that become references (`OrderedPackageMedia`: part name, SHA-256, content type, size, bytes), in the package's order. It checks no content: the organiser's own pictures are kept as they are. The server calls it once on the organiser's Word file (`openOrderedWordFile(...).base`), when it makes the room, and stores each one under its hash before it writes the first checkpoint.
  - **Writing.** `writeOrderedCheckpoint(doc, base, { media, write })` takes the options of `writeOrderedPackage` (`OrderedPackageWriteOptions`) and writes front to back through the same zip writer, the manifest last before the central directory. It never reads a picture: the file's own media and the media that changes added become references by their hash. It reads `media` only for an ink part that a change added, which stays inside, one at a time.
  - **Reading.** `openOrderedCheckpoint(bytes, { file })` opens a checkpoint as `openOrderedWordFile` opens the Word file it stands for: the same bounded read, normalization and load, so every copy holds the same items under the same addresses. It reads no media bytes. The manifest is untrusted: at most the engine's limit of one part (`XML_HARD_MAX_BYTES`, 64 MiB), strict JSON, every field checked (a canonical part name that the package does not hold, a SHA-256 of 64 lower-case hex digits, a type that becomes a reference and that the package's content types give the part, a size of at least one byte, a free place among the entries). Another format is refused as `checkpoint-format`, another version (versions 1 to 4 too) as `checkpoint-version`, a manifest that does not read or fit as `checkpoint-manifest`, and a file with no manifest as `not-checkpoint` (all `OrderedWordFileError`). The writer checks the same limit: `writeOrderedCheckpoint` refuses a larger manifest as `too-many-items`, and the host keeps its last checkpoint and the log. `openOrderedWordFile` refuses a file that holds the manifest's part name (`checkpoint`), so an upload is never taken for a checkpoint and a checkpoint is never opened as a Word file. The document's `resources.fileMedia` lists the references (`OrderedFileMedia`, by part name key); their part names are taken (`fileParts`), so no change adds a part under one.
  - **Compose and save.** Compose puts an empty part at each reference's place first (`compose/file-media.ts`), so the engine's own rules keep or drop it as they keep or drop a part with bytes (a deleted picture's part goes), and puts the bytes in last: `orderedPackageBytes` and `composeOrderedPackage` from `blobs` (missing bytes refuse as `missing-blob`, or a screen leaves the part out and keeps its relationship), `writeOrderedPackage` through `media`, one at a time, when its entry is written. A document loaded from a checkpoint saves byte for byte as one loaded from the Word file it came from (`__tests__/checkpoint.test.ts`).
  - **Pages.** A client opens the room's file by its content: a checkpoint when it holds the manifest, else a Word file. It reads every reference through its `media` reader, with the same reads and the same join wait as the session's own pictures, and checks only the size and the hash: the file's own media is not checked by content. Every published document shows each one once it reads (`OrderedPublisher` keeps each reference's place). A read that fails is reported (`missing-blob`, or `invalid-media` for bytes of another size or hash) and tried again after a rejoin; the picture stays in the document and in every save. A change that copies the file's media names its hash: the room's storage holds it, so the session marks it stored at the join and no upload starts (`batch.partMedia`; other bytes under the same part name are new media and go through the upload). The room's media check admits a change that names a reference's hash (`room/room.ts`). `OrderedLocalRoomOptions.blobs` gives a local room the media its storage holds from the start. Tests: `__tests__/checkpoint.test.ts`, `__tests__/client/editor-checkpoint.test.ts` (two editors and one room whose file is a checkpoint).
  - **Fold rules.** Each field of the room's model has a rule for how a fold keeps it, in `__tests__/fold-rules.test.ts`: read back from the Word file (the load step), kept in the manifest (the section and field), made again from other facts, or not needed after a fold (such as the undo history). Each table covers every key of its type, so a new model field fails the type check until it has a rule there. A field that a fold neither reads back, nor keeps, nor can leave out is marked `open` with its known difference. The test also checks that the writer writes and the reader reads each manifest field a rule names, and that every section the writer writes has a rule.

- **A Word file without comments (`compose/without-comments.ts`).** A host that keeps a copy with comments and a final file without them builds the room's document once and writes it twice: `writeOrderedPackage(doc, base, { media, write })`, then `writeOrderedPackage(doc, base, { media, write, comments: 'remove' })` (`OrderedPackageCommentOptions`; `orderedPackageBytes` and `composeOrderedPackage` take it too and give the same bytes). The option changes the composed package only, never the document, so the two calls work in either order. With `remove`, compose writes no comment of the room, and after the whole compose, before the media bytes go in, one pass takes out every `w:commentRangeStart`, `w:commentRangeEnd` and `w:commentReference` from every XML part (a story, a text box in its host part, any other part), with a run that a reference leaves holding only its properties, as the engine's comment delete drops one. The comments, commentsExtended, commentsIds and commentsExtensible parts go with their relationships and content-type Overrides, for every owner that relates one, found by relationship type through the engine's `withoutPart`; a part that only removed parts name goes too, in turn (a picture in a comment, a chart's workbook, style and colors), so its bytes are not read. Replies go with the rest. Tracked changes and their ids, bookmarks, fields, notes, the people part (it also names the authors of tracked changes) and every other part stay as `keep` writes them; a tracked change that held only a comment reference stays, empty. When `withoutPart` refuses (an owner's relationships kept only as bytes), the writer refuses the file as `engine-refused` before it writes a byte, never a half stripped file. `keep` is the default and writes today's bytes. A checkpoint keeps every comment. Today's path through `editor-api` (`body.getComments()`, `comment.delete()`, save) reaches only the body's own comments: it leaves a comment in a text box, a header, a footer or a note, keeps the four comment parts with their relationships and Overrides, keeps every commentsExtensible entry, and keeps a comment's picture; where it removes a comment, its stories equal this pass's. Tests: `__tests__/without-comments.test.ts` (a thread with replies and the four parts, a header, a footer, a footnote, a text box, a range across a table, references inside a tracked insertion and a tracked deletion, a file with no comments, the room's comment, reply and resolve, the streaming writer, the refusal, a chart in a comment), `__tests__/client/editor-without-comments.test.ts` (two editors and one room).
- **The client side (group 9.4).** The session holds media in one store by hash, `OrderedMedia` (`client/media.ts`): the bytes of its own new pictures, and the bytes it read back. It checks bytes by content before it holds or keeps them: the content type on the list, the image's signature and header (`client/media-check.ts`: a raster image through `validateEmbeddedImageBytes`, with the engine's pixel caps; an SVG, TIFF, EMF or WMF of a paste as D18 says), at most 25 MiB (an SVG at most 2 MiB), and for bytes read back the hash and the size the change named. Sending: the replica gives the unsent changes in order up to the first one whose media the room does not store yet (`takeUnsent` with the session's `mediaReady`); for that one, `OrderedMedia.ready` starts the host's upload once (`client/media-uploads.ts`, at most four at once, as the reads) and the session holds it, and every later change, until the upload answers `stored`. A refusal takes back the changes that name the hash by name (`ordered-refused`, reason `blob-refused`, detail the storage's code), as a room refusal does, and sends the rest. A failed upload goes again after the reconnect delays (`reconnectDelays`, one step more for each failed try), and at once after a rejoin; without timers, only after a rejoin. An upload does not depend on the room's connection: one in flight when the connection drops goes on, and its answer counts. A blob the storage stored stays stored. The session aborts its uploads (`signal`) when it ends: `destroy`, a `reload`, or a fatal error. Reading: after the join's catch-up and after every room change, the session reads each picture the list shows and the store lacks, four at a time, through the host's `media(location, sha256)` reader (an option beside `wordFile`), from `welcome.blobs` only; never from an address a file or a change holds. A picture that reads publishes again (the media part and its relationship appear); one that does not is reported (`missing-blob`, or `invalid-media` for bytes that do not check). The join waits for the catch-up's reads for at most the join timeout, so the first document holds them.
- **The entry point for other media (group 9.10, paste).** The editor gives the gate the package its ops apply to: `gateOperations(ops, scope, { package })` (`CollaborationGateContext`), the package after the write's own package edits, so it holds a new picture's media part and relationships. Every write the editor commits passes it: the op lane, the preview and the headless automation host build it from the write's package edits (`collaboration/gate-context.ts`, built only when a session reads it), a paste gives the package its merge made, and the picture writes give the package they built (D16). The session reads it only when a translator asks. A translator calls `batch.media(part, relationshipId)`: it resolves the image relationship of `part` in that package (an internal part only; an external picture is never fetched), holds the bytes under their hash, and returns the change's media value (`{ sha256, contentType, size }`). It returns null when that package has no image there, and refuses by name when the bytes are over the room's cap for their type (`media-too-large`, detail the type) or are not an image the room stores (`invalid-media`). The change kind lists the hash in its spec's `blobs`. The session does the rest: the upload before the change, the wait, the refusal, the tries again, and the reads on other copies.

### D15. Review actions from the editor (task 9.3)

The editor commits accept, reject and comment writes through `commitReviewOps`, outside its op lane, so a collaboration gate saw an empty batch: the ordered client refused them all as `ordered-opaque-write`. Two small editor changes give the gate what it needs, with no change for other sessions:

- `EditorCollaborationSession` has an optional member, `gateReviewWrite(write, scope)`, with `CollaborationReviewWrite`: the write's intent, the ops it commits (when the editor plans them before the commit), and a new comment's text and range. A session without the member is asked `gateOperations([], scope)` as before, so the Yjs session in `packages/pro` sees no change.
- `commitReviewOps(run, intent)` also takes a `ReviewWrite` in place of the intent. The review commands plan their ops before the commit and pass them: one card's accept or reject (`resolutionOps`), accept all and reject all (the planner's `acceptAllRevisions` and `rejectAllRevisions` with the marks' node ids), and a change of suggestions' author (`setRevisionAttribution`, group 9.10). `run` commits exactly the ops the gate saw. A new comment passes its text and range.

What the ordered client makes of them:

- **Accept and reject.** Each op names revisions by `w:id`, `w:author` and `w:date`, or by the node ids of their marks in the package the client last published (the editor shows that package). Compose writes a suggestion's `w:id` for each role as a function of the suggestion's id (`revisionIdFor`), so the client indexes its suggestions by triple, for the authors and dates the ops name only. Every decision op of one write (accept all, reject all, the planner's ops over several parts, a choice of cards) makes one `decide` change that names each card the ops reach, with the versions this copy shows (`orderedCardSeen`, the seen check of D6): the first decision op makes it, from the revisions every decision op names, read before it applies. So the room orders one change and every copy lays its pages out once. The decision applies on the copy at once, as the editor committed it, and goes to the room in the next batch; the room leaves a card that changed first (the copy shows it again when the room's change replaces its own), refuses the change as `stale-decision` when every card changed, and as `policy-decide` when the sender is a party (the party rule: decisions are the organiser's alone). A refused decision is taken back on the copy and the cards show again. The host's request for several cards (`requestDecisions`, the host's Accept all) is the same change. Tracked changes to style definitions are cards too (decided by default, as in Word and the editor alone). Word keeps a change of a style in the styles part: a style's `w:pPrChange` and `w:rPrChange`, a table style's `w:tblPrChange`, `w:trPrChange` and `w:tcPrChange` (also in a conditional format, `w:tblStylePr`), and the document defaults' records. The editor alone shows the records of one element with one `w:id`, author and date as one card (`revisionGroupKey`) and decides it with the engine's resolver: an accept drops the record, a reject puts back the properties it recorded. No edit makes one; only the Word file brings them. Load (`load/part-revisions.ts`, after the stories, so their ids stay) makes one pending suggestion for each such card, with no items, in `doc.partRevisions` (`OrderedPartRevision`: the part, the element, the three values and the style id). Every copy loads the same file in the same order, so every copy has the same ids. Its card holds it alone (`orderedCards` lists these cards after the story cards); a decision names it as any other card, so Accept All and Reject All take it in the same one change, and the seen check and the per-card rule hold as for every card. A decision only turns its status, and compose writes the styles part from the file's with the decided records resolved by the engine, in creation order (`compose/part-revisions.ts`, `withDecidedPartRevisions`): in the save before the resources, and at each publish from the file's part, cached by the statuses. A decision or a take-back of one on such a card sends the package (`dirty.stale`), so every editor gets the styles part and lays out again: a rejected style change shows the old formatting on every screen. A decision has no undo here either (the next bullet); the 2.x Yjs room had one (`packages/pro/src/collaboration/__tests__/document-style-revisions.test.ts`). The editor names a style's records by their node ids; the client finds the card by the part, the element and the three values (`outsideRoom` in `client/ops/review.ts`), never by the three values alone: Word numbers a style's records from 0 as it numbers the body's, so s2's style record has the `w:id`, author and date of a body suggestion, and before, the editor's accept of the style card decided the body card. A record the engine cannot decide both ways (no author, which the editor alone shows read-only; no recorded old properties, which it cannot reject) has no suggestion: the editor's Accept All decides every other card and says so once by name (`not-in-room`, with the parts in the detail), and the publish takes the editor's own write there back; a write that reaches nothing else is refused by name. Not covered: the numbering part's records (a list level's `w:pPrChange` or `w:rPrChange`), which the editor alone shows no card for and does not decide, where Word does: a known difference of the editor alone. Tests: `__tests__/part-revisions.test.ts` and `__tests__/client/editor-style-revisions.test.ts` (two real editors: one style card accepted and rejected beside the body card with the same three values, Accept All and Reject All with body cards in one change, the editor alone's styles part, the host's request, a late joiner, save and reopen, a party's refused decision). A run with nothing in it but its properties loads as one zero-width item, kept whole; it keeps the file's format record (`w:rPrChange`) as its suggestion's, and compose writes its properties as a decision leaves them (`decidedRunShell`). Before, the run stayed as the file wrote it, so after a decision on a revision it shares with runs of words (s2's `w:id="0"`) its record stayed in every copy and a card stayed on every screen. Such a record with a revision of its own is a card of its own (`orderedCards` notes a pending format record on a zero-width item that shows), as the editor alone shows it; before, the cards read only units with a width, so a host's Accept all did not name it and it stayed in the save (`client/editor-empty-run-format.test.ts`). A host maps a review item to its suggestions with `orderedSuggestionsOfRevision(doc, { part, id, author, date, element })`: the pending suggestions the editor's decision of that item reaches, with the same index, limited to the part (outside the stories, by the element too), so a dashboard card never guesses by author and second (`client/editor-revision-suggestions.test.ts`). A card holds what policy 3 joins, so an accept of one revision decides its whole card, as the host decides cards. A reject of one revision that is the sender's own change inside another author's suggestion (a reply on that author's card) is a `retract` of that change only, as the editor alone and Word reject it: deciding the card rejected the other author's words too (the host's Undo my edit, found by the live run of the 2.x flows; `client/editor-own-reply-reject.test.ts`). The sender's undo of that reject gives the change back, as the editor's undo does (`withdrewAll` in `client/undo.ts`). A file's own `w:sectPrChange`, `w:tblPrExChange`, `w:numberingChange` and `w:numPr/w:ins` are suggestions since group 9.8 (`load/sections.ts`, `load/properties.ts`), decided as every other. A `w:tblGridChange` names no author (`CT_Markup`): it is the table record of the suggestion whose table properties role writes its `w:id` (task 9.7).
- **A decision has no undo.** It enters the history as a step with no inverse, so the organiser's undo refuses it by name (`no-inverse`, detail `decided`) and the step goes. Since task 9.12 every direct edit has an inverse; a decision is no direct edit, so it keeps none. A comment never enters the undo history (D15). The host's earlier rooms have no undo for a decision either: the server applies it.
- **Comments travel through the room (task 9.17).** A discussion is a real Word comment, made, answered and resolved through the room as a suggestion is. This reverses the earlier rule that a Word comment's text had no place in the change format, when the host kept the text in its own backend and the document held only a `thread:<n>` marker. The reasons: the text, the replies, the resolved state, the person and the date then live in the Word file and the checkpoints; every page sees them in the room's order with the edits; the room checks them with its policy and stamps the person, so no one writes under another name; and the host keeps no second store that can drift from the document. Three change kinds, handled by name as the first kinds are: `comment` (a new thread on the units from `from` to `to` of one story, a caret allowed, with `text`), `comment-reply` (`text` answering the thread of comment `comment`, by its `w:id`) and `comment-resolve` (the thread of comment `comment`, with an optional `note`). A reply answers the thread's first comment, as Word's threads are flat, and its range sits on that comment's, after the thread's earlier replies, as the engine anchors a reply over its parent's range (`coincidentInsertIndex`): its start after the starts that follow the comment's start, its end before the ends in front of the comment's end, its reference after the references that follow the comment's reference. So a thread's starts and references run oldest first and its ends the other way, as the editor alone writes them, and Word's save, which writes `comments.xml` in the body's order, keeps the thread in date order. Before, each reply went next to the first comment, in front of the earlier replies, and Word's save listed the thread newest first. Where another comment's end or reference is in front of the first comment's start at the same place, the engine puts a reply's start in front of them and so in front of the first comment's start; the room keeps it after, in the thread's order. A resolve adds its note as the sender's last reply, then resolves every comment of the thread, as the engine resolves a thread. The text is plain text with a paragraph for each line (`\n`), of 1 to 10,000 UTF-16 units (`ORDERED_CHANGE_LIMITS.comment`). No edit, no delete and no reopen in this version: a deleted comment's text would stay in the log. The model holds a room comment in `doc.comments` as it holds a file's (`OrderedComment`, with `person`, null for a file's comment): its `w:id` is a Word decimal and its paragraphs' `w14:paraId`s are minted from the change id, past the file's comment ids, every comment's paraIds and this session's new paragraphs, so every copy writes the same; its element is built once at apply by the engine's builder (`commentElementOf`: the paraIds, the `CommentText` and `CommentReference` styles, `xml:space` for edge spaces). Its range is three zero-width items, as a file's load gives them, and `doc.commentRanges` names each comment's markers (load writes the file's). A reply to or a resolve of a file's comment with no `w14:paraId` gives that comment one, as the engine does (`stampedParagraph`). Every write is in the change's undo record, so the room and the client take a refused or pending comment back. Compose writes the comment parts from the model (`compose/comments.ts`): `comments.xml` is the file's children with each comment as the model holds it, then the room's comments; `commentsExtended.xml` keeps the file's entries, rewrites `w15:done` where the model resolved a comment (the engine's `withResolvedDone`), and adds an entry for each comment the file does not hold, each resolved comment with none, and the comment each of those answers, so both ends of every thread are written (Word drops a thread whose parent has no entry, and a room comment with no entry on another comment's words would read as its reply). `commentsIds` and `commentsExtensible` keep the file's entries; the engine writes none for a new comment. A part the model leaves as the file had it stays the file's own object, so a file the room did not comment on saves as it came, and a file with no comment and no room comment writes no comment part. The client composes the comment parts again only after a write that changed comments (`OrderedDirty.comments`). The editor's Add comment (`gateReviewWrite`, intent `comment-add`, with its text and range) becomes a `comment` change. The editor's reply, resolve and delete name no comment of the room and stay refused: the editor gives the gate no ops for them (`ordered-opaque-write`). A host writes through the session: `addComment(text, from, to)`, `addSelectionComment(text)` (the selection the editor last published, read as places of the copy as the caret is read for typing), `replyToComment(comment, text)` and `resolveComment(comment, note?)`. Each is made on the copy at once and sent in the next batch, and a refusal takes it back and reports through `onRefused`; they return the new comment's id, whose person `orderedDocument().comments` gives. Comments never enter the undo history, as Word and Google Docs keep them out. The policy's rules are in D9. A comment's words deleted stay discussed: a direct deletion that covers a comment's whole range keeps its three markers, so the comment stays at the deletion's place as a range of no words (placement rule 12 now takes only a bookmark), for a file's and a room's comment alike. The editor alone takes the comment away with its words; that difference is on purpose and the matrix lists it (`known.ts`). A tracked deletion keeps the comment over the struck words, and its acceptance leaves a range of no words.
- **The file's comments (task 9.16).** Load reads the main document's comments part, the one Word and the editor read, into `doc.comments` (`load/comments.ts`): one `OrderedComment` for each `w:comment` of the part's root, by `w:id` in the part's order (the first one when the file repeats an id). A record holds the author, initials and date, the body's `w14:paraId` values and the last one (the key of `commentsExtended` and `commentsIds`), the durable id and the `commentsExtensible` entry when the file has them, and the `w:comment` element as the file wrote it: a rich body, a picture or a field is kept, never rebuilt. The thread and the resolved state come from the editor's own review reader (`commentItemsOf` over `commentsOfPart`, `threadStateOfPart` and every story's anchors), so a room lists the threads the editor alone lists: `w15:paraIdParent`, then `w16cid:parentId`, then a comment over exactly another's words when it has no thread entry, and an entry that names no comment, names its own comment or closes a cycle is ignored as the editor ignores it. The deletion index (`indexCommentThread`) is not used: it makes the whole file flat for one bad entry, and its scan budget stops short of a large comments part. Each comment's nodes count against the load's item limit. While no change touches them, compose writes the file's comment parts as they came (the bullet before), and a checkpoint opens to the same comments under any file number. Tests: `__tests__/comments-load.test.ts` and `__tests__/client/editor-comments-load.test.ts`.

Tests: `__tests__/client/editor-review-actions.test.ts`, with real editors, one room and a review module that derives the engine's own cards (core's tests may not import `@docx-editor.dev/pro`): one card accepted and rejected, accept all and reject all, a party's accept refused by the party rule, a stale card, no undo of a decision, and save and reopen. `__tests__/client/editor-comments-room.test.ts`: a party's comment on every page with its person, through save, reopen, a checkpoint and the next room; a reply and its thread entries; the organiser's resolve with a note, a party's resolve and a late reply refused; a reply to and a resolve of the file's own thread; a comment on another person's suggestion; a direct and a tracked deletion of a comment's words, accepted and rejected; two comments on overlapping and on the same words; a reply the room orders after the resolve; a comment sent again after a restart; the editor's own comment writes; and a thread's order (the markers of a thread with two replies and a resolve note from three persons, equal to the editor alone's on every page and after save and reopen; the thread in date order after Word's reorder of the comments; a reply to the file's thread; replies from two pages at once; a page's undo of its own typing). `__tests__/room-policy-comments.test.ts`: the policy's comment rules and limits.

### D16. Pictures and shapes (task 9.4)

What Word writes decides what a party may suggest. Evidence: ECMA-376 Part 1 lists every revision element in `wml.xsd` (lines 803 to 955 in `reference/ecma-376/part1/schemas/`); the only one that can hold a drawing is `w:ins`, `w:del`, `w:moveFrom` or `w:moveTo` around a `w:r` whose content is `w:drawing` (`CT_RunTrackChange`). `CT_RPrChange` holds character properties only, and `CT_Drawing`, `CT_Inline`, `CT_Anchor`, `CT_NonVisualDrawingProps`, `CT_Transform2D`, `CT_RelativeRect` and the lock types have no change child, so no file can record an earlier size, crop, position, wrap, rotation, alt text, lock, link or image. Word 2016 files (LibreOffice bugs 128913, 143042, 143043) show a new picture or shape as `w:ins` around its run and a deleted one as `w:del` around its run, with no `w:delText`. Word's own handling of a property change with tracking on (applied untracked, or a deletion and an insertion of the whole picture for Change Picture) is not documented; a check in desktop Word is open.

- **Change kinds** (`change/kinds/pictures.ts`). `insert-object`: a new inline picture (its media by hash, extent, title, description, link, a locked aspect) or a text box (its width), before a place; a suggestion or a direct edit. `object-property`: a direct edit of one object, the ops of one editor command in order (resize, crop, position, wrap, metadata with a link, locks, transform), so one command is one undo step. `object-resource`: a direct new image for a picture. A deletion is the format's `delete` over the object's unit. Every value is typed and bounded (`pictures-read.ts`): sizes as positive coordinates, offsets in the ranges OOXML allows, a crop below the whole image, alt text by the engine's own metadata rule (up to 2048 units, tab, line feed and return allowed), a link through `sanitizeHref`. No XML travels: a new drawing is built on every copy by the engine's own builders and run through the engine's `insertDrawing` on a scratch part, its ids from the change (`wp:docPr/@id` a decimal above any file's dense ids).
- **Properties are records, not results.** A property change is an `object` record on the atom (`model/objects.ts`): the engine's op, which compose runs, with the other accepted records, in creation order on the object's own element (`compose/objects.ts`), so the object keeps its node id (the editor's selection holds) and `revert` of one record takes back exactly that edit while later ones stay. A record whose op no longer applies (a lock another record set) is skipped, as the engine refuses it. A property change in `suggest` mode is refused (`untracked-only`); the editor refuses it itself in suggesting mode.
- **Media and relationships** are resources (D14) of the suggestion that holds the atom: a party's pending insertion, a direct edit's settled suggestion, or another person's pending insertion when the organiser inserts inside it. So a reject, a take-back or a `revert` takes the part out of the file. A save also drops a loaded picture's image relationship and media part once the session made them unused (an accepted deletion, a new image), as the editor alone does (`compose/unused-media.ts`); an orphan the file came with stays.
- **The party rules** are the host's earlier check. A new picture or a deletion is a suggestion. A property change or a new image made with tracking off changes only the package: `policy-direct` with reason `package`. An untracked insertion or deletion changes the text (the engine's paragraph text counts a picture as one character): `policy-direct` with reason `text`. Nothing else is refused: no picture edit is one Word refuses.

### D17. Tables (task 9.7)

The organiser's table edits are direct, as the editor alone makes them with tracking off. A party's edits are suggestions in the form the engine writes in suggesting mode. Word reads and decides each one (`reference/ecma-376/part1/schemas/wml.xsd`):

| Edit | A party's suggestion | A decision |
| --- | --- | --- |
| Insert a row | `w:trPr/w:ins`, `w:cellIns` on its cells | Rejected, the row goes with what is in it. |
| Delete a row | `w:trPr/w:del`, `w:cellDel` on its cells | Accepted, the row goes with what is in it. |
| Insert a column | `w:cellIns` on each new cell (`CT_TcPr`, a `CT_TrackChange`). The neighbour lends half its width, with no change record, as the engine writes it. | Rejected, the neighbour gets its width back by the engine's rule (`rebuildRevisionTable`: a removed cell's grid space goes to the cell before it, or at the row's start to the first one after it), from the table before the decision: the cell the column took width from at the width it lent, any other cell as it shows. |
| Delete a column | `w:cellDel` on each cell of the column | Accepted, the neighbour takes its width by the same rule. |
| Drag a column edge or the right edge | `w:tblGridChange` with the old grid (`CT_TblGridChange` extends `CT_Markup`: an id, no author), `w:tblPrChange`, and `w:tcPrChange` on every cell of each row, under one revision | One card: the grid record goes with the cell records. A decision by the author's address (the records that carry an author) takes the grid record along (`gestureGridSites`), so the order of decisions after a reopen does not change the result. |
| Table style, header rows, alignment, widths | `w:tblPrChange` (and `w:tblGridChange` for widths) | As any property record. |

### D19. Links, fields, bookmarks and a table of contents (task 9.5)

Every edit writes what the engine's own op writes, so the room's copy and the editor alone save the same Word file (`__tests__/client/editor-links.test.ts`, `editor-fields.test.ts`, `editor-bookmarks-toc.test.ts` compare them). Kinds: `insert-link`, `remove-link` (`change/kinds/links-fields.ts`); `insert-field`, `field-code`, `field-result`, `toc-pages`, `bookmark`, `insert-toc`, `toc-result` (`change/kinds/fields.ts`).

- **Links.** Word has no revision for a link: `w:hyperlink` is in `EG_PContent` only, never inside `w:ins`, and `CT_Hyperlink` has no change record (ECMA-376 Part 1, `wml.xsd`). The organiser's link edits are in place; a party's are the editor's proposal (the words struck and a copy linked or unlinked). A link's address is its suggestion's relationship resource (D14), so a rejected or taken-back link leaves none, unless a rejected new link still holds something (see "A link a decision leaves with only markers").
- **Page fields.** A field is one object: begin, instruction, separator and end in one run, built by the engine's `pageFieldContentBuilders`, typed by the placement rules of a tab. Tracked, the whole field is one `w:ins`, as the engine and Word write it, so a reject takes it all back. Word writes each `w:fldChar` and the instruction in a run of its own, and a result run; the engine's one run is valid (`CT_R` holds any number of them), and a load reads it in any place: beside or inside a link, after or inside another field, in a revision (`__tests__/field-containers.test.ts`). The editor's command needs an open header or footer, where a party is refused by the furniture rule; the editing API's lane types one in the body.
- **A field's instruction and result.** The engine's own op (`setFieldCode`, `refreshFieldResults`) runs on a scratch paragraph that holds only the field, and the field's item is replaced: the old one struck, the new one inserted after it, with the same face and records. The organiser's undo shows the old field again. A suggesting change would save as Word's tracked field update (the old runs in `w:del` with `w:delInstrText`, the new ones in `w:ins`); the editor sends these ops untracked, so a party's is refused by the host's party rule (`package` for an instruction, `text` for a result). A format over a field reaches its result runs (`setRunProperties` with `targetRunIds`): one `format` of the field's item with what the press changes on the named run. A field in a pending move's destination is moved content: the engine's field locator skips only `w:ins` and `w:del`, so the engine rewrites it in place, and the room rewrites it too; the new item stays in the move, so it goes with a rejected move, and the organiser's undo deletes it as text typed inside another person's insertion. A field in a pending insertion, deletion or move source stays refused (`invalid-edit`), as the engine leaves it.
- **A field whose result is a link.** A whole field is one unit, as the engine counts it, but one unit cannot hold a link or a revision that starts or ends inside the field: a table of contents field over one paragraph, its result the row's link (Word's form for a one-row table of contents, and the room's after a refresh to one row and a join), or a suggestion in a field's result. Such a field loads as its markers and its result, as a field over two paragraphs does and as the room holds it (`offsetIndexOf`, `load/paragraph.ts`). Before, the load gathered the link's runs into the field's unit and lost the revision marks inside it; a reopen then wrote the runs outside the link, an empty link after the field, and no suggestion (acceptance room s2-short, a page field after the row; `__tests__/field-containers.test.ts`). A field inside another field's result in that field's paragraph is no unit to the engine: its field parse stops at a begin with no end in the paragraph (a field that ends in a later paragraph), and a closed field's result is that field's; the layout shows no field there either. A reopen would hold no unit and no card for it, so the room refuses to make one there (`invalid-edit`, as for a field it may not rewrite), for the organiser and parties alike: a new page field and a field's new instruction or result (`refuseFieldInField`, `field-depth.ts`). A paste makes no complex field (the engine's paste keeps none). After the outer field's end, or in a paragraph it only passes through, a field is one unit as before. Reading such a field as a unit in the engine is later work.
- **Results that depend on layout.** A field result, a contents row's text and a page number come in the change as text. The editor that makes the change computes them once from its own layout; every other copy writes that text and never lays the document out to find it. Copies lay out with different fonts and screens, so a result computed on each copy could differ; text in the change cannot. A new PAGE or NUMPAGES field is saved with an empty result, as the engine saves it; the editor paints the live number.
- **Bookmarks.** A bookmark is no revision: `w:bookmarkStart` and `w:bookmarkEnd` carry no author or date and no change record names them (`CT_Bookmark`, `CT_MarkupRange`), so Word and the engine write them directly with Track Changes on. `bookmark` is a direct edit only, and a party's is refused by the host's party rule (`package`). New markers go where the engine's `markerSiteAt` puts them (past every container that ends at the place, before a marker already there); their `w:id` is a Word decimal minted from the change, so it does not depend on the order of changes. A name in use moves: the change names every shown marker of the name (a removed end is the end of a shown start of the name, by its `w:id`; another bookmark's end is refused, `invalid-edit`), and the client adds one change for each other story that holds it (the editor removes it there with a package edit, which the gate does not see).
- **A table of contents.** Insert and refresh are direct edits only: the engine has no tracked form, and a party's is refused by the host's party rule (`text`). The engine's builders make the rows from the rows in the change, with each heading's symbols read from the heading paragraph as the list shows it. A refresh strikes every unit between the field's separator and its end and puts the new rows right after the separator, the first one in the separator's paragraph, as `replaceTocResult` does. The separator and the end must be one TOC field's own pair, and the result must hold every container it opens: a copy refuses a change by name (`not-one-field`) when the field's instruction is no `TOC`, the separator is inside a link or another inline container, the end is the end of a field inside the result (a row's `PAGEREF`) or of a later field, or the end is inside a link. Such a change leaves a container's open item in one paragraph and its close item in another, so no copy composes the part, and every later save of the room fails (cell x68-short, seed 1012, change `olive-1:807`; `__tests__/fields-apply.test.ts`). The page pass rewrites each row's last text: a `PAGEREF` field's result (`field-result` with `last`) or plain text (`toc-pages`). The editor publishes the room's copy between a contents write and its page pass (`flushPendingJournals`), so the pass names nodes the client knows. The engine treats a result as generated and read-only, so no one's suggestion is inside it.
- **One undo step for a contents command.** Word's Update Table is one undo step. The rows and each page pass commit apart, because a pass needs the layout the rows made, so the editor alone made two or more steps; it now runs each contents command in one history group (`inOneUndoStep`, `paginated-surface.ts`). The gate is told the commit's group (`CollaborationGateContext.historyGroup`), and the client joins a commit to the top step when both have the same group, as the store joins its entries (`history.ts`, `recordCommit`). So one undo takes a refresh back in the room too (`editor-bookmarks-toc.test.ts`, `toc-refresh.test.ts`: the rows push a heading to the next page, so the page pass writes). Word evidence for the one step waits for Word.
- **Known difference from Word: typing in a contents result.** Word lets a person type in a table of contents' rows; its next Update Table replaces that text. The editor alone paints the rows read-only (a click on a row goes to its heading, the caret steps over the field), and the room refuses an edit in a contents paragraph (`not-covered`, `refuseLocked` in `placement.ts`). The room refuses what the TOC field covers, as the editor's read-only ranges give it (`tocParagraphRanges`): from the field's begin to its end. The control's heading before the field ("Contents") and a paragraph after it are ordinary text, as in Word and the editor alone: the organiser types there directly and a party suggests (`tocFieldRange` in `placement.ts`). A contents control with no field is generated whole. Deferred for the first release: typed text in a result has no lasting effect in a contract, because the next update replaces it, and Word's form needs a rework of the editor's contents design for every user (a plain click places the caret and Ctrl+Click follows the link; the hover frame and the right-click menu find the contents without read-only rows; 16 editor tests check the current design). The editing API (`editor-api`) has no path into an ordered room, so its runtime notes do not change. Open task 12.1; a likely start is a `result` extent on `TocParagraphRange` and `lockedTocAtPosition` for the read-only places.
- **A move into a link or a control.** A move's half inside a link, a control or another inline container gets its range markers inside that container (each holds `EG_PContent`, and range markup is part of it), and a file's `w:moveTo` after its author's move range ended is not read as part of that move. Before, the saved half was a bare `w:moveTo`, which a reopened file joined to another move of its author, under that move's date and Word id (the 50-page acceptance run, seed 1006; the random paste session, seed 71; `__tests__/move-into-link.test.ts`). Engine fix: a control's content with move range markers stayed typed only for bookmark and comment markers, so a Word file with a tracked move in a control lost its typed control (`store/package/ooxml-sdt.ts`). Seed 71 also showed a control's value record that wrote `w:showingPlcHdr` before `w:placeholder`, against the `CT_SdtPr` sequence; the record now keeps schema order (`__tests__/prompt-record-order.test.ts`). A file's move range with no moved word drawn in it is passed over (`emptyMoveEdges`, `compose/inline.ts`), as the room draws no range around no words: a control's prompt shown again where the moved words all went is no moved word, so a decision gives the same file live and after a fold (`__tests__/checkpoint-fold-prompts.test.ts`). A load gives a range end to the move its `w:id` names (the range start's), and to the move of the last wrapper before it only when no start has that id: ranges can nest, as after a fold a move to a paragraph's end goes inside another move's range there, and before, the outer range's end went with the inner move, so an accept of the outer move left it (the fold shapes session, seed 78; `__tests__/checkpoint-fold-moves.test.ts`). Before, a live move had none (compose drew its range round its wrappers), so a later move or typing at the end of its words went after its range live, and inside it after a fold and in the editor alone (seed 78; `__tests__/checkpoint-fold-moves.test.ts`, `__tests__/client/editor-move-ranges.test.ts`). A load notes every part's revision ids before it reads a story, so an id it gives such markers never repeats one a later part holds. A control's prompt shown again goes before a move's range markers that no shown word follows, as compose draws none (`promptPlace`, `change/settle-emptied.ts`; seed 6 of the fold shapes session). Word evidence on such nesting is still to come; the editor alone is the reference.
- **A link a decision leaves with only markers.** Word's Reject All keeps a rejected new link that still holds a comment's start, with its relationship and address; only a link left with nothing goes (Word evidence: `c-link.docx` to `c-out-reject.docx`, Reject All with tracking off, in `/tmp/word-evidence-links/`: `<w:hyperlink r:id="rId4"><w:commentRangeStart w:id="0"/></w:hyperlink>` and its relationship stay). The engine's decision and a reopened room file already did so (a file's link belongs to no suggestion); the live room dropped the link with its rejected suggestion, and its address (the random two-person session, seed 103). Now the live drawing keeps a link edge that only a decision's rejection of the link's insertion hides, while the link holds something shown, each half of a split link alone (`compose/kept-links.ts`, in the drawing and in the view), and compose writes a link's address while a written link names it, whatever its suggestion's status (`compose/resources.ts`). A take-back (its author's, or the organiser's undo of a direct link) is no decision: the link goes with its address and the markers stay (`__tests__/link-left-with-markers.test.ts`, `store/__tests__/revision-resolve.test.ts`). A kept link takes the same edits as a link in a reopened file: the lookups of a link edit (`shownItemAt` in `edits/places.ts`, the client's `containerOf`) accept it (`isKeptLink`). A party's new address for a link copies only the words that show; before, a `link-target` change also copied text a decision had taken out of the link (the editor sends its own copy, so its edits were right).
- **A join inside a batch.** The engine keeps the first paragraph's node id across a join, so a later op of the same batch names the joined paragraph by it. The batch resolves an id it has read already to the shown paragraph that holds it now; before, the organiser's deletion across three or more paragraphs was refused as `out-of-step`.

### How to add a group

A group of section 9 (9.4 to 9.10) adds its work in its own files, so several helpers work at once and meet only in short lists:

1. `client/ops/<group>.ts` holds the group's ops. For each op, set `status: 'translated'`, the change kinds, and a translator made with `translator(kind, (op, batch) => ...)`. The translator checks the op's options at once and throws `OrderedClientRefusal` for one it does not say. It returns a step that reads the list through `batch` when it runs. A new option goes in the group's options list.
2. `change/kinds/<group>.ts` holds the group's new change kinds. Add the change interface (extending `OrderedEditBase` with its own `kind`) to the group's union type. Add its spec, made with `orderedKindSpec`, to the group's table. A spec says how the validator reads the payload (readers of `read.ts` and `values.ts`, every value bounded; every path starts at the change, `at(fields.path, key)`, so that a refusal names its place in the message, `changes[k].…`, and a server does not read it as a bad frame: `__tests__/change-validate.test.ts` checks every family), what the change touches (through the target reader), how it applies (model mutations only, inside the caller's undo record), what the suggestions-only policy reads (`text`, `properties`, `beside`), and what the publish composes (`paragraphs` or `story`). The validator, the targets, the apply, the policy, the publish and the caret ask the registry for the kind, so no shared file changes.
3. `edits/<group>.ts` holds the group's model edits. They write through `model/mutations.ts` and mint every id from the change's `orderedIdMinter`.
4. A resource the group adds outside the story text (media, a relationship, a list definition, a style, a header part, a setting) goes through `model/resources.ts` (D14).
5. Tests: the group's matrix scenarios, two editors and one room, the party rules, save and reopen, and the group's line of `STILL_PLANNED` in `__tests__/client/op-coverage.test.ts` taken off. Update the group's rows in the D13 table: the guard test checks the state there.

Shared lists a group may still touch: a new refusal reason in `model/refusal.ts` (one line), and the group's line in the guard test. Nothing else.

### D21. Headers, footers and sections (task 9.8)

The group's eight ops are translated (`client/ops/sections.ts`) into four change kinds (`change/kinds/sections/`): `section-property`, `header-footer`, `section-break` and `watermark`, and the `setting` kind of D18 for odd and even pages. A change names a section by the item that holds its `w:sectPr`: a paragraph mark, or the body's section item. The body's item exists at a fixed address even when the file wrote no body section, so every copy names it alike. A change to a section is a record on that item (`model/sections.ts`). Compose runs the engine's own write for that one section again: the accepted records first, then the pending ones under one `w:sectPrChange`, as Word keeps one record for each section.

| Edit | Organiser | Party | Word's form |
| --- | --- | --- | --- |
| Page size, orientation, margins | Direct, or a suggestion in suggesting mode | A suggestion; refused on a section that holds another person's pending section record (`policy-not-own`, `others_suggestions`) | `w:sectPrChange` with the complete earlier section. Word for Mac wrote `w:orient="portrait"` in the record on 2026-10-29 (`/tmp/word-evidence-sections/page2-tracked.docx`). |
| Section break | Direct, or a suggestion on the organiser's own new mark | A suggestion on the party's own new mark; refused when it retypes the next section (`policy-direct`, `package`), and when the section it cuts holds another person's pending section record, which the new section would copy inside the party's suggestion (`policy-nested`, `nested`, as Enter in D9) | The mark proposed (`w:pPr/w:rPr/w:ins` and `w:sectPr`), and the next section's `w:type` untracked (`/tmp/word-evidence-sections/break2-tracked.docx`). |
| A different first page, the header and footer distances | Direct, or a suggestion in suggesting mode | A suggestion; refused on a section that holds another person's pending section record (`policy-not-own`, `others_suggestions`) | `w:sectPrChange`, one "revision section property" in Word for Mac on 2026-10-30: "Formatted: Different first page header", its record `<w:titlePg w:val="0"/>` (`/tmp/word-evidence-sections/~$titlepg-tracked.docx`); "Formatted: Header distance from edge", its record the old `w:pgMar` (`~$hdrdist-tracked.docx`). - **Parts.** A new header or footer part is a `story` resource with its relationship (D14). Every copy gives it the same part name and relationship id. A rejected or undone one leaves no part behind on save. A picture watermark names its bytes by their SHA-256; the session uploads them before the change, as for a new picture (D16).
- **Page setup.** It goes to the sections the document has when the change applies: every one, or the one that governs a paragraph then. So a section break that another person made first takes it too, as in Word one after the other. A section holds one `w:sectPrChange`, so a second page setup there would take the earlier record over, and the earlier change would lose its author. A party's is refused (`policy-not-own`, `others_suggestions`), as the host's earlier check refuses it: every party change stays tracked under its own author. The organiser's direct page setup adds a decided write and takes over no record; the organiser's suggestion there takes the record over (policy 2), as a format does. A direct page setup, furniture option or section type over another person's pending record names it (`over`), so a reject of that record takes the direct write away too, as Word and the editor restore the record's section; before, the room kept the direct write and a folded copy lost it. A header or footer reference is in no record and names none (`section-kinds-decisions.test.ts`, `client/editor-sections-over-pending.test.ts`). A suggested page setup or furniture option that leaves a section as it shows makes no record (`sectionOpKeeps`, the engine's own writer and record rule), as the engine and Word record none.
- **A break's copy.** A break's new section copies the section it cuts as it shows without its pending tracked writes, and without the direct writes made over them, which Word's one record holds with them, as the copy's own record (`sectionWithoutPendingWrites`). Another person's pending break there gives the section it ends, so a decision on that break leaves the copy as it is, as in the editor alone. The pending tracked writes go with the copy under their own suggestions, with the direct writes made over them (`madeOverWhere`), so a reject of the copy's record takes those away there too, as Word's reject of the copied record does; for a party, another person's such write refuses the break (`policy-nested`). A revert of the organiser's direct break on an existing paragraph mark takes every other record on its section off the mark, and its redo copies the pending ones again (`settleRevertedBreaks`): before, the copied records drew the section again, so the break stayed, kept the other person's card on the mark, and a later reject drew the section with its page size only (`section-break-revert.test.ts`). The editor's own break rides on Enter's new mark, which its revert hides, so this reaches a client that sends a break on an existing mark.
- **The type of the next section.** A suggested break that gives the next section another type writes that type as a record that stays when the suggestion is rejected (`keptOnReject`): Word writes it untracked, so a reject leaves it. A take-back removes it, as the editor's undo does. A party's such break is refused: the host's earlier check rejects the party's suggestions and sees the type stay. Another person's pending record on that section holds the section before its own change with the type, as the editor keeps that record, and a record on the break's new section holds the whole copy: compose lays every write Word makes untracked under the change record (`sectionAfter`). A file's record that stands (that person's record after a fold, before the break) holds the type the same way. Before, a checkpoint wrote the type into that person's `w:sectPrChange` as their change, so a reject gave the earlier type after a fold and kept it in the room (`section-break-type.test.ts`). Word's form: the tracked break proposes the mark and writes the next section's `w:type` untracked (Word for Mac, `break2-tracked.docx`, 2026-10-29); a reject removes the mark and its section properties, so the text joins the next section, which keeps its type (ECMA-376 Part 1, §17.6.17), as the editor's reject does.
- **The form of a reject.** The editor alone's reject of a page setup writes the earlier page as Word's reject does: the margins in full, as the record holds them, and the page size without the default `w:orient="portrait"` that the record states (Word for Mac, reject all, `page2-rejected.docx`). The room's reject of its own section write gives the same form (`applyDecided` in `compose/sections.ts`), as a reopened room does with the file's record, so a fold changes no reject. A file's record that stands holds the old values of the writes drawn over it, as the file states them (the engine keeps a standing record). A direct write's take-back gives the section back as it was, as the editor's undo does. The matrix compares a reject by the effective page.
- **A file's own `w:sectPrChange`** loads as a suggestion on the section's item and is decided as one (`load/sections.ts`).
- **Editor fixes to match Word.** In suggesting mode the editor now records page setup as `w:sectPrChange` (before, it had no tracked form). It inserts a break that retypes the next section, with that type untracked (before, it refused that break). The editor removes a watermark's own run whole, as Word does, instead of leaving an empty picture. A rejected page setup leaves the default orientation out, as Word's reject does. A file's own `w:numberingChange` is one revision whose accept and reject both remove it (before, the editor did not list it, and Accept All left it in the file). A different first page and the header and footer distances are recorded as `w:sectPrChange` in suggesting mode (before, they were written untracked); a rejected different first page leaves no `w:titlePg`, and a restored one goes back in schema order. A tracked page setup on the body's own section shows its card at the document's last paragraph mark (before, the card had no place).
- **A file's own `w:tblPrExChange` and `w:numberingChange`.** Word for Mac counts each as one revision (2026-10-29, `tblprex2.docx`, `numchange.docx` in `/tmp/word-evidence-sections/`). A row's `w:tblPrExChange`: accept keeps the row's new `w:tblPrEx`, reject gives the old one back. Word's reject also lays the row out again (`w:gridAfter`, a new grid); that is a layout recompute, and neither the engine nor the room copies it. Both load as suggestions (organiser decisions only; a party's is `policy-decide`) and decide as the editor alone does. A rejected row record (`w:trPrChange`, `w:tblPrExChange`, `w:tcPrChange`) gives the row's cells that hold no record of their own default formatting, as the engine's reject does (`compose/row-cells.ts`, the engine's `restoreUnrecordedCells`, confirmed against Word). The room's own tracked row writes record every cell of the row, so in practice this reaches a file's own records. The engine decides in order: a cell's record decided before the row's leaves the cell with no record, and the row's reject resets it; the room, whose decisions give one result in every order, takes the result of the row first. A first-edition `w:numberingChange` (not in the current schema): accept and reject both remove the record and keep the list; compose writes it back into `w:numPr` while its suggestion is pending. A tracked list membership (`w:numPr/w:ins`) is decided the same way: the engine keeps `w:numPr` on accept and on reject alike (`validNumberingRevision`), so the room loads it as the same kind of record, and the two go back in `CT_NumPr` order. A party's decision on either is refused (`policy-decide`); a save while one is pending writes it as the file had it, and the reopened room decides it. A party's change that writes a paragraph record (a list change, an alignment, any `paragraph-property`) on a paragraph that holds another person's pending numbering record is refused once applied (`policy-not-own`, `others_suggestions`, `room/suggestions-only.ts` `othersNumbering`): it would drop the record or copy it into the party's own record, and Word decides the numbering with the paragraph's properties record, so an accept or a reject of the party's record settles the other person's numbering too (Word for Mac, 2026-11-25: a tracked alignment over another author's `w:numPr/w:ins`, either decision removes their `w:ins`). A change that leaves the paragraph as it is writes no record and passes: the same list and level again changes nothing, in Word (no revision), the engine (`setListNumbering` keeps the reference and its record) and the room. The organiser's direct list change there is not affected.

## Risks / Trade-offs

- [Engine drift in placement] → the matrix runs in CI; the client publishes the list's paragraph.
- [Word form cannot hold some states after a close] → policies 1 and 2 remove 341 of the 357 decisions that changed after save and reopen in the spike; compose writes hidden prompts as glossary blocks for the other 16 (task 0.3). The random sessions found three more limits (a direct run or paragraph change after a pending one; a second change to the same cell or table properties); they are documented and become matrix scenarios (task 4.4). The first now goes with the pending change's reject, as Word's one record gives it (D5 policy 2).
- [Full-page relayout on Enter, Backspace across paragraphs, and header changes] → measured at six sizes with layout; if slow, an editor change passes the exact changed-paragraph list.
- [zstd is experimental in Node] → one interface; gzip fallback.
- [Rooms that never close] → change file grows; the server logs a warning past 100,000 changes.
